# Issue 唯一标题契约 · ISSUE_CONTRACT

> **定位**：治理「协作 Issue 名字不唯一、有重复、没真正启用」的结构性方案。
> 机器可执行实现在 `local-agent/expertise/issue_contract.py`（**唯一事实源**），
> 本文件负责说清契约、判据与处置流程。
> 与 `docs/ISSUE_MANAGEMENT.md`（模块/Agent 双版本管理）配套：那里管**版本线**，这里管**身份唯一性**。

## 一、问题（实测数据）

2026-11-03 对 `dongdongxiaozu/dongjiagoushi` 做全量清点，open Issue 共 **50** 个，其中：

| 标题 | 数量 | 性质 |
|---|---|---|
| `测试登录模块` | 8 | 联调测试流，标题互相不可区分 |
| `评审登录模块` | 8 | 同上 |
| `开发登录模块` | 7 | 同上 |
| `聚合页控制动作演示` | 7 | 同上 |
| `CLI控制台发起` | 6 | 同上 |
| `云端开发请求：对齐登录模块PR产出` | 2 | **同名重复** |
| `云端开发请求：本地测试先行门` / `云端开发请求：补齐本地测试先行门` | 1 + 1 | **近重复**（同一诉求两种写法） |

即 **36/50（72%）是低信号或重复 Issue**。根因不是人粗心，而是：

1. **派发器没有身份约束** —— 任意调用方把自由文本当标题建 Issue；
2. **联调/测试流与真实工作流共用同一空间** —— `entries.cnb_live` 每条云开发请求都自动建一个锚点 Issue，
   标题直接取测试字符串（`CLI控制台发起`），于是每次联调都留下一条垃圾；
3. **没有幂等** —— 同一诉求重跑一次就多一个 Issue，久而久之无法检索、无人认领，即"没真的启用"。

> 关键结论：**去重不能靠事后人工**（50 条清一次，下周又长回来）。必须让"建 Issue"这一步
> 在结构上不可能产生重复。

## 二、契约

### 2.1 标题形态（唯一合法形态）

```
<类型>:<模块> · <唯一键>
```

- **类型**（受限集，不许自造）：`FEAT` `BUG` `FIX` `DOCS` `CHORE` `TEST` `REL` `RFC`
- **模块**（白名单，见 `MODULE_WHITELIST`；新模块须先登记）：如 `expertise`、`platform-adapter`、`reviewer`
- **唯一键**：稳定、可寻址、人可读，只允许 `[a-z0-9._-]`，长度 2–61，如 `pareto-frontier`、`gate-v1`

示例：

```
FEAT:expertise · pareto-frontier
FIX :platform-adapter · cnb-live-anchor-noise
DOCS:issue-contract · unique-title-enforcement
```

> 反例（一律拒绝）：`CLI控制台发起`、`测试登录模块`、`优化一下`、`FEAT:expertise · p0`（占位键）。

### 2.2 唯一性判据

唯一性由 **`(类型, 模块, 唯一键)` 三元组** 判定（`issue_key()`），标题只是它的渲染形态。
因此大小写、空格、全角半角漂移**不会**产生第二个 Issue：

```
"feat:expertise · Pareto-Frontier"  ==  "FEAT:expertise · pareto-frontier"
```

### 2.3 幂等派发（`plan()`）

给定「现有 Issue 清单」+「期望派发清单」，输出四类动作，**绝不重复建**：

| 动作 | 含义 |
|---|---|
| `create` | 该 key 不存在 → 建 |
| `reuse` | 该 key 已存在 → **复用不再新建**（同批内重复也只建一次） |
| `duplicates` | 同一 key 有多个号 → 进收并 |
| `rejected` | 低信号/不合契约 → **建之前就拦下** |

### 2.4 收并（`dedupe_plan()`）

同一标题多号 → 保留一个主号（默认最小编号，可改"评论最多者"），其余关闭并回指主号，
自动生成闭环注释。近重复（不同标题但相似度 ≥0.9）单独列为 `near_duplicates` 供人工判断 ——
**语义重合不自动合并**（避免误伤），只把事实摆出来。

### 2.5 正文契约（agent-ready brief）

Issue 正文必须含五段（与 `docs/ISSUE_TRACKING.md` 对齐），缺段即判不合规：

1. `## 目标`
2. `## 做/不做边界`
3. `## 验收标准`
4. `## 外部验证`（**必须列可真实执行的验证命令**，不能只写"已测试"）
5. `## 信息来源与时效`（每条事实带 `source` + `dated_at`）

外加 `## 版本声明`：`module_version` / `agent_version` / `depends_on`（双版本管理，见 ISSUE_MANAGEMENT.md）。

## 三、处置流程（把历史遗留收干净）

```
① 清点 epilogue：拉全量 open Issue（含已关闭）
② 演练（dry-run）：dedupe_plan() 生成收并计划 —— 不写云端
③ 人工确认：核对 near_duplicates（语义判断交人）
④ 执行：按计划打收并注释 + 关闭重复号；测试流批量打标签并关闭
⑤ 启用：后续所有派发走 plan()，幂等 + 契约校验
```

**执行原则**：
- 先 dry-run 出计划，人确认后再写云端（不可逆动作不自动执行）；
- 关闭一律带**收并注释回指主号**，不静默消失；
- 低信号测试流**不删除**（保留审计痕迹），而是**打标签 + 关闭**；
- 重复号的评论内容不丢，主号可见可追溯。

## 四、防复发（结构性约束）

| 层 | 约束 | 失败时 |
|---|---|---|
| 派发器 | 所有建 Issue 必须经 `guard_create()` / `guard_issue_title()` | 直连 API 建 Issue 视为违规 |
| 契约 | 标题不合规即 `rejected` | 不让垃圾进仓库 |
| 正文 | 五段缺一即不合规 | `validate_body()` 拦截 |
| 演练 | 批量操作先 dry-run | 不可逆动作先出计划再执行 |
| 信号灯 | `test_expertise.sh` E8/E9/E10 | 契约被改坏即红灯 |

### 4.1 接线（v0.2.0 → v0.2.1 · 从「有引擎」到「真生效」）

只造出 `plan()` 不算落实——**谁不调它谁就绕过**。2026-11-14 实测正是这样：契约已合进
main，可派发器仍用自由文本当标题，同一天又长出「开发 / 评审 / 测试登录模块」三条。

现在把 `guard_create()` 挂到**建 Issue 的唯一出口**上：

| 出口 | 接线点 | 行为 |
|---|---|---|
| 经理派发 L2 | `dispatch_engine._create_issue()` → `guard_issue_title()` | 低信号标题契约化；同 key / 同名复用返回既有编号，**不再新建** |
| bridge 云开发锚点 | `entries.cnb_live.send()` → `_gate_title()` | 同诉求 → 同 key → 复用既有锚点 Issue |
| 批量提交 | `hybrid.batch._create_issue()` | 读真实存量过闸门；`reuse` 直接返回既有编号，`reject` 中止提交 |
| 手工治理 | `scripts/issue-contract.py` | audit / plan / dedupe（dry-run 默认），与派发器共用同一读法 |

**三处出口各写一份读法 = 三层都会坏**。v0.2.0 正是这么坏的：两处各写了一份
`--state all`（`issues list-issues` 只认 `open`/`closed`，传 `all` 实测 400），
又都不查 `returncode`，错误文本被当 Issue 清单解析 → 存量恒为 `[]` → `reuse` 分支
一次都进不去。**闸门看着接上了，真实环境一条都没堵住。**

v0.2.1 把「读存量」收成唯一实现 `expertise/issue_source.py`，三条硬约束：

1. **全量 = 分别拉 `open` + `closed` 再合并**（`all` 非法；不带 `--state` 实测只回 open，
   218 条已关闭的看不见）；
2. **严判 rc / errcode，任一页失败整体失败**，绝不把错误响应当清单解析；
3. **失败不写缓存、新建回填**——一次 400 不许污染整个进程；建成功后 `remember()`
   让同批第 2 条起也能去重（否则同批内去重不成立，只有跨进程去重）。

**唯一键不许塌缩**（v0.2.1 最要紧的一条）：中文被 `_SLUG_RE` 整段剔掉后只剩英文残片，
`API 接口改造` / `登录模块 API` / `开发登录模块 API` 会全塌成 `api` —— 第二条诉求过闸门
命中 `reuse`，直接被并进第一件事的 Issue，**新任务永远不会被建**。比原来的重复更糟。
现在判据是「有没有丢弃实质内容」：

| 原文 | 唯一键 | 说明 |
|---|---|---|
| `refactor login module` | `refactor-login-module` | 全 ascii，可读优先 |
| `update README 说明文档` | `update-readme-41dd91a6` | 可读残片 + 内容摘要后缀 |
| `开发登录模块` | `task-8d0f0b8499ae9cd9` | 残片代表不了原意 → 纯摘要 |

`derive` 之后还会**再复核一次** `is_low_signal`：`p0`/`tmp`/`todo` 这类占位词当唯一键
被明确判为低信号，却在 v0.2.0 被原样放行；现在命中即换摘要键重 derive，仍不合格才 reject。

**降级不假装**：契约不可用时降级为原样创建，但 `reason` 里写明「存量读取失败，幂等降级」
和具体错误——宁可噪音留在明面上，也不做「看起来守着契约其实没有」。

信号灯分两层（**只看源码字符串 = 假信号灯**）：

- **E9 接线存在**：`inspect.getsource` 断言三处出口真有闸门调用、且都不再自写存量读法；
- **E10 行为为真**：假 runner 注入 400 / 半途失败 / 同批重复 / 不同诉求塌缩，
  断言「失败不污染缓存」「建完回填能 reuse」「不同诉求必须不同键」「action 分支真判」。

## 五、已知边界

1. **不自动改写既有标题** —— 历史标题保留原样做审计，只做"收并关闭"，不做批量改名（改名会破坏外部引用）。
2. **近重复需人工判断** —— 相似度只提示，不做语义合并。
3. **契约判定不直连网络** —— `issue_contract` 只产出动作与证据，可在本地单测、可 dry-run；
   唯一的网络入口是 `issue_source`（读存量 / 回填），它把 rc、errcode、分页失败**全部显式
   判定后再交给契约**，读失败即幂等降级并写进 `reason`，不静默冒充"没有存量"。
4. **读存量有进程内缓存** —— 成功才缓存（一次 400 不污染），因此**跨机器/跨进程**看到的
   存量以云端为准；同进程内新建由 `remember()` 回填，不需要重读。
