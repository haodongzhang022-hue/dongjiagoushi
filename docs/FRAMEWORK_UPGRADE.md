# 框架自升级闭环（FRAMEWORK_UPGRADE）

> **为什么要这份文档？**
> 模块（`arch-skill`/`memory`/`dashboard`/…）与 agent 角色（`架构·总师`/`架构·开发`/…）各有独立的版本演进线，
> 但「框架自身」——统领所有这些模块与角色的那个整体——此前**没有一个显式的升级评估入口**，
> 容易像 `memory` 模块当初那样游离于版本管理之外，成为版本管理的盲区。
>
> 本文件把「框架自升级」**显式纳入架构**：定义何时触发框架升级、怎么评估、怎么留痕，
> 让框架整体与模块/agent 一样拥有版本演进线，可被人类俯瞰、可被 AI 追踪。

---

## 一、什么是"框架自升级"

框架 = `AGENTS.md` + `.cnb.yml`（流水线）+ `.codebuddy/skills/architect/SKILL.md`（方法论）+ `.cnb/settings.yml`（角色骨架）+ `docs/`（顶层架构与治理文档）+ `src/memory/`（记忆库与语义触发）这一个**整体**。

- **模块升级**：某单个模块能力增强（如 `memory` 升 v0.2.0）——在模块版本线上演进。
- **agent 升级**：某单个角色人设/契约增强——在 agent 版本线上演进。
- **框架自升级（本文件）**：**跨模块 / 方法论 / 治理规则 / 测试红线**层面的整体调整——在 `framework` 模块版本线上演进。

当一个改动**跨越多个模块**，或触及**方法论本身**（八步流程、协作协议、安全护栏、版本治理规则），或改变**测试红线**（新增/收紧验收信号灯）时，它就是**框架级升级**，应走本闭环。

---

## 二、何时触发框架自升级（触发条件）

满足以下任一即应发起一次框架自升级评估（`type=upgrade`）：

| 触发信号 | 举例 |
|---------|------|
| 🔀 跨模块改动 | 一次 PR 同时改动 memory + dashboard + 测试脚本 |
| 🧭 方法论调整 | 架构八步增/改步骤、协作协议（接力/回转/打断）变更、安全护栏（CP）调整 |
| 📐 治理规则变化 | Issue 版本管理机制、双版本规则、命名规范 调整 |
| 🧪 测试红线变化 | 新增测试脚本、收紧验收标准、改变信号灯判定 |
| 🧠 智能化能力演进 | 语义触发 / 记忆库 / embedding 能力整体升级 |
| 🚨 自审查发现薄弱点 | 架构师自审查 / 用户反馈暴露的框架级缺口 |

**自评估入口**：任何 agent 或人类协作者，发现上述信号，即发起一次「框架自升级」Issue（`module: framework / type: upgrade`），并按下方第三节流程评估。

---

## 三、框架自升级评估流程（八步走一遍的轻量版）

一次框架自升级 = **用架构八步对本框架做一次自审**（这正是 `#4` 真实场景跑通的方式）。落地为 4 个步骤：

```
① 触发  ② 评估（八步自审）  ③ 决策（CP）  ④ 落地留痕
```

1. **触发**：按第二节条件，发起 `type=upgrade` Issue（声明头见下）。
2. **评估（八步自审）**：以 `架构·总师` 身份对框架做一次轻量自审——
   - 现状盘点（各模块/agent/测试信号灯版本）
   - 识别薄弱点与升级项（分级 🔴必修 / 🟡建议 / 🟢优化）
   - 升级项是否跨模块 / 是否动方法论 / 是否动测试红线
   - 输出：**框架自升级评估表**（见下）。
3. **决策（CP）**：评估结果交人类拍板——采纳哪些升级项、先做哪些；**未获 CP 放行不得落地大改**。
4. **落地留痕**：获放行后落地，升级项每个都留痕于 Issue/PR/提交/CI，并在本文档「版本演进」与看板登记。

### 框架自升级评估表模板

```
---
module:         framework
module_version: <落地后 framework 达到的版本>   # 与已有 framework 版本线一致
type:           upgrade                        # 框架级升级专用类型
target:         <本次框架升级目标>
update:         <相对上一版本的升级内容（跨模块/方法论/测试红线）>
depends_on:     <前置框架升级 issue 编号，若无则留空>
---

## 框架自升级评估表
| 升级项 | 级别(🔴/🟡/🟢) | 跨模块? | 动方法论? | 动测试红线? | 落地方式 |
|--------|------------|--------|----------|------------|---------|
| <升级项> | 🔴 | 是/否 | 是/否 | 是/否 | <PR/Issue/文档> |

## 触发信号
<命中第二节哪一条>

## 决策
- [ ] CP 已获人类放行（未放行不得落地）
```

## 四、版本演进（framework 模块版本线）

`framework` 作为独立模块纳入双版本治理，与 `arch-skill`/`memory` 等一样有一条模块版本演进线。
**版本强制**：`module: framework / module_version: vX.Y.Z / type: upgrade`。

| 版本 | type | 日期 | 升级内容（跨模块/方法论/测试红线） | 落地 PR |
|------|------|------|----------------------------------|---------|
| v0.1.0 | init | 2026-08 | 确立「框架自升级」闭环：FRAMEWORK_UPGRADE.md + upgrade 类型 + framework 模块版本线；memory 挂真实 embedding；文档-实现一致性测试；看板加框架健康度 | PR 见本 Issue |

> 登记规则：每次框架自升级落地，在本文档「版本演进」表顶格追加一行，并同步刷新 `docs/DASHBOARD.md` 的「框架健康度」维度与 `docs/ROADMAP.md` 里程碑。

---

## 五、与既有治理的关系

| 既有机制 | 与框架自升级的关系 |
|---------|-------------------|
| Issue 双版本管理（ISSUE_MANAGEMENT.md） | `framework` 是**又一个模块**，纳入 `module_version` 版本线；`type=upgrade` 为框架级专用类型 |
| 架构八步（SKILL.md） | 框架自升级评估 = 对框架做一次轻量八步自审 |
| 测试信号灯（tests + .cnb.yml test） | 框架升级若动测试红线，必须同步更新测试并保持全绿 |
| 看板（DASHBOARD.md） | 「框架健康度」维度展示 framework 模块版本线 + 各模块/角色版本 + 测试信号灯 + 待办升级项 |
| 安全护栏（AGENTS.md CP1/CP2/CP3） | 框架自升级属**大改**，落地前必须经 CP 放行，禁止代替用户确认 |
