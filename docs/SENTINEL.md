# 防无效努力 · 目标收敛监控（SENTINEL）

> 本文件描述本仓库的**「架构·监控哨兵」（Sentinel）**机制 —— 让团队
> **稳定运行、不出错、不陷入无意义循环、不在同一件事上反复尝试同一个错误**，
> 通过**量化到目标的进度距离**做机器判定，命中即触发「打断 → 重新规划 → 上报局部调整」，
> **防止无效努力、防止目标偏差**。
>
> 对应 ISSUE #25；可执行载体 `local-agent/sentinel/` + 角色 `roles/sentinel.py`。

---

## 一、问题诊断：为什么团队会「无效努力」

| 用户原话要点 | 现状缺陷 | 缺什么 |
|--------------|----------|--------|
| 「控制团队稳定运行、不出错、不陷入无意义循环」 | 只有「回转(打回)/打断(中断续跑)」**协议**，无**量化监管**——不知道"是否真的在收敛" | 到目标的**量化距离** |
| 「不在同一个事情上反复尝试同一个错误」 | 重复失败靠人肉发现，机器无法识别"同一失败反复提交" | **重复错误检测** |
| 「持续距离目标近似距离、反复横跳达不到」 | 无距离序列，无法判定"原地打转 / 来回摆动" | **停滞 + 横跳检测** |
| 「触发机制：打断他，根据目标任务和当前距离重新规划内容分配」 | 打断无"剩余距离"依据，重规划无量化输入 | **按剩余距离重规划** |
| 「触发第二次，提交给架构师的助理，讨论是否架构要局部调整」 | 无二级升级通道 | **上报架构师助理 + 局部调整** |
| 「防止无效努力、防止目标偏差」 | 无统一"距北极星的量化距离"口径 | **目标进度尺** |

**结论**：现有 `progress` 只记录"发生了什么事"，没有**"距目标还剩多远 / 是否真的在靠近"**
这一可机器判定的量化维度。本机制补上这块，形成独立的**监控哨兵**横切层。

## 三、核心机制

### 1. 目标进度尺（量化距离，统一口径）

每个角色领取任务后，为任务建立**目标进度尺**，每次推进写一条刻度：

```
goal_meters:
  meter_id   目标刻度 id（g-<task_id>）
  goal_total 目标总量（北极星，0..goal_total）
  current    当前已达量
  distance   = goal_total - current   ← 到目标的量化距离（越小越近）
  delta      = 本次 distance - 上次 distance（负=在靠近，0=停滞，正=回退/横跳）
  note       本次说明（失败须显式标错，如"报错/重试/失败"）
```

**为什么用「距离」而非「完成百分比」**：百分比丢失了"还剩多少"的绝对值，无法判定
"接近但迟迟不越过"的横跳；距离序列让"是否真的在收敛"变成**可比较、可阈值判定**的数值。

### 2. 机器判定（detect）—— 三类无效努力

| 信号 | 判定条件（默认参数，可注入） | 含义 |
|------|------------------------------|------|
| **stagnation 停滞** | 连续 `n` 次距离变化绝对值 < `eps` | 原地打转，未推进 |
| **oscillation 横跳** | 窗口内距离摆动够大 + 方向交替够多 + 净推进 < 阈值 | 反复来回，迟迟不越过 |
| **repeated_error 重复错误** | 同一 agent 同一任务，**显式标错**(note 含"失败/报错/重试"等)的同型失败 >= n 次 | 反复尝试同一个错误 |

**不误伤**：普通推进 note（如"稳步推进"）不参与重复错误判定；单调推进即使多次记录也放行。

### 3. 处置协议（engine）—— 分级升级

```
每次推进 → track 记录刻度 → detect 判定
  ├─ 未命中 → 放行，继续推进
  ├─ 命中 1 级 → [打断] + 依据「剩余距离」重新规划再分配（留痕 sentinel_actions）
  │              打回原角色按其剩余距离重规划，交回下游复评（沿用回转协议）
  └─ 命中 2 级（同任务二度）→ 上报「架构·总师助理」
                讨论是否对架构做局部调整（目标定义/分配/流程），
                标 blocked 待人工/总师介入，不自行放行
```

- **1 级（打断重规划）**：发 `[打断]`，把 `distance`（剩余距离）作为**重规划输入**，
  让被打断角色依据"目标 + 当前距离"重新规划内容与分配，禁止在同类失败上反复尝试。
- **2 级（上报局部调整）**：同一任务**第二次命中**即升级。交给「架构·总师助理」
  评估"是否架构局部要调整"——因为连续无效努力往往意味着**目标定义/分配/流程本身有问题**，
  而非执行者努力不够。标 `blocked`，待人工/总师拍板后才放行。

## 六、小组长监督（进度尺 · 小组视角）

用户诉求：「进度的尺 小组长也应该能监督」。

进度尺（`goal_meters`）按**小组(group_id)** 归集（agents 表 group_id 关联），
架构·小组长可用 `sentinel.engine.group_oversight(group_id)` 获取**本组成员**每个任务
到目标的收敛视图（二级信息）：

```
group_oversight('g-登录组') → {
  group_id, count,
  meters: [ { task_id, agent_id, target, goal_total, current,
              distance, progress_ratio, delta, note, ts } ... ]
}
```

- **小组长监督**与**哨兵机器判定**互补：哨兵负责机器判定 + 处置协议（打断/上报），
  小组长负责从**组视角俯瞰**本组成员是否在收敛、及时协调调度；
- 若小组长发现本组某成员迟迟不收敛（distance 不降 / delta 不改善），可联动哨兵介入。

## 七、一句话总结

**目标进度尺量化「到北极星还剩多远」，机器判定「是否真的在收敛」，
命中即按剩余距离打断重规划、二度即上报架构师助理评估局部调整**——
让团队不再为无效努力空转，主动显式暴露并规避目标偏差。
