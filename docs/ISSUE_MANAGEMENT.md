# Issue 声明与模块版本管理机制

> 本机制解决一个核心问题：**多个 Issue 之间不是互不相关的平铺项，而是同一模块能力的「版本化演进线」。**
> 每个 Issue 声明自己所属的模块、目标、版本号与更新内容，从而让「开发好开发、合并好合并、可灵活接着继续开发」，模块能力呈**阶段性、可多次被加强**。

## 一、背景与动机

在架构师 Agent 框架中，很多模块能力是**阶段性**的，会在一系列 Issue 中被**多次加强**（如 `.codebuddy/skills/architect` 从 v0.1 不断迭代到 v0.3+）。

若不声明归属与版本，Issue 会变成同层级的散点：

- 开发时不知道这个 Issue 属于哪个模块、基于哪个版本。
- 合并时看不出模块版本走到了哪里，容易冲突、漏合、乱合。
- 想接着开发时，无法快速定位模块当前版本与待办路径。

**引入「声明头 + 模块版本线」后**：

| 环节 | 收益 |
|------|------|
| 开发 | 开发人员一眼看到「模块 + 类型 + 目标版本」，上下文聚焦，不偏差 |
| 合并 | 每个 `update`/`fix` Issue 对应**明确的版本变更**，合并=版本生效，冲突面收敛 |
| 持续开发 | 新 Issue 通过 `depends_on` 挂到父模块线上，版本号串联，可随时接着加强 |
| 观测/决策 | 模块版本线即「能力成熟度看板」，人类可俯瞰每个模块演进到哪一步 |

## 二、核心概念

### 1. 模块（Module）= 版本管理的原子单位
- 一个模块有唯一 `module` ID（如 `arch-skill`、`issue-mgmt`、`pipeline`、`knowledge`）。
- 每个模块独立维护一条**语义化版本线** `vMAJOR.MINOR.PATCH`。

### 2. Issue 声明头（front-matter）
每个 Issue 顶部声明五个字段，把 Issue 锚定到某模块的某个版本目标上：

```yaml
module:     <模块ID>        # 所属模块
type:       init|update|fix|standalone
target:     <本 issue 目标>
version:    <目标版本号>      # 落地后模块达到的版本
update:     <相对上一版本改了什么>
depends_on: <父模块 issue / 前置 issue 编号>
```

### 3. Issue 类型（type）与版本动作

| type | 含义 | 版本动作 | 是否版本管理 |
|------|------|----------|--------------|
| `init` | 模块建立 / 首个版本 | 创建模块根节点，`v0.1.0` | ✅ |
| `update` | 能力增强 / 阶段性迭代 | `MINOR` 升级（`v0.2.0`） | ✅ |
| `fix` | 缺陷修复 / 小改 | `PATCH` 升级（`v0.2.1`） | ✅ |
| `standalone` | 一次性任务 | 不改变模块能力 | ❌ |

### 4. Issue 关系层级
Issue 不是同层散点，而是挂在「模块根 issue」下的演进树：

```
模块「issue-mgmt」版本演进线
    ├── issue#10  type=init   v0.1.0   ← 模块根节点（depends_on 无）
    ├── issue#15  type=update v0.2.0   depends_on:#10
    ├── issue#18  type=fix    v0.2.1   depends_on:#15
    └── issue#22  type=update v0.3.0   depends_on:#10
```

## 三、与「接力卡」的关系（本次落地的 A 方案）

架构八步中需要分工协作时，架构师通过**接力卡**召唤协作角色。接力卡载体采用你确认的 **A 方案：Issue 评论内嵌结构化卡片**（轻量、天然留痕、可版本追溯）。

- **Issue 本身**：承载「模块声明 + 版本 + 目标」，是任务的**版本锚点**。
- **Issue 评论**：承载「接力卡」（任务书 + 当前进度 + 下一步），是协作的**上下文传递**。
- 二者结合：Issue 声明确定**做什么、是哪个版本**；评论接力卡确定**谁来做、进行到哪**。

```yaml
# 接力卡内嵌卡片（评论中）
---
任务书: <目标+边界+验收>
输入上下文: <模块/版本/前置产物>
当前进度: <已完成/卡点>
下一步: <待办>
接手角色: <PM/DEV/CR/QA>
---
```

## 四、版本号规则

- 采用语义化版本 `vMAJOR.MINOR.PATCH`。
- `init` → `v0.1.0`；`update` → 升 `MINOR`；`fix` → 升 `PATCH`。
- 同一模块并发 Issue 由版本号串联，**先到先合并**；若并发冲突，按版本线依次合，避免同版本覆盖。
- `standalone` 不占用版本号，不污染模块版本线。

## 六、对本框架的意义

- 让「模块化、可独立演进」理念**落地到 Issue 管理粒度**：每个模块都有自己的版本线，能力可被多次阶段性加强。
- 让人类观察者的「二级信息」多一个维度：**模块版本演进看板**（哪个模块走到 v 多少、待办是哪些）。
- 让架构师 / 开发 / 评审 / 测试的上下文**有明确的版本锚点**，杜绝「改的是哪一版」的混乱。
