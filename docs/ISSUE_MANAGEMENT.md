# Issue 声明与模块/Agent 双版本管理机制

> 本机制解决两个核心问题：
> 1. **多个 Issue 之间不是互不相关的平铺项**，而是同一模块/同一 agent 能力的「版本化演进线」。
> 2. **版本不是"整体版本"，而是「模块版本」与「agent 版本」两个独立维度**，各自以**较小的迭代单位**独立推进——避免"局部迭代却强推整体版本"导致的并发合并冲突、合并失效。
>
> 每个 Issue 声明自己所属模块与 agent 角色的目标版本与更新内容，从而让「开发好开发、合并好合并、可灵活接着继续开发」，模块与 agent 能力呈**阶段性、可多次被加强**。

---

## 一、背景与动机

在架构师 Agent 框架中，能力是**阶段性**的，会在一系列 Issue 中被**多次加强**：
- **模块能力**（如 `arch-skill`、`multirole`、`knowledge`、`dashboard`、`testing`）会从 v0.1 不断迭代到 v0.3+；
- **agent 角色能力**（如 `架构·总师`、`架构·产品` 的人设、输出契约、协作协议）也会独立迭代。

若不声明归属与版本，Issue 会变成同层级的散点：
- 开发时不知道这个 Issue 属于哪个模块、哪个 agent、基于哪个版本；
- 合并时看不出模块/agent 版本走到了哪里，容易冲突、漏合、乱合；
- 想接着开发时，无法快速定位当前版本与待办路径。

**更关键的是：** 若只用一个"整体版本号"，当一个 Issue 的改动跨越多个模块/agent 时，多个并行 Issue 会为**同一个版本号**竞争——局部迭代一多，合并就互相冲突、反复失效。所以必须**把版本拆成「模块维度 + agent 维度」两个独立版本**，让每个 Issue 只落在**一个最小迭代单位**上。

| 维度 | 含义 | 演进单位 |
|------|------|----------|
| `module_version` | 所属**模块**能力的成熟度 | 每次只针对一个模块升版 |
| `agent_version` | 所属 **agent 角色**能力的成熟度 | 每次只针对一个角色升版 |

### 引入「声明头 + 双版本线」后

| 环节 | 收益 |
|------|------|
| 开发 | 开发人员一眼看到「模块 + agent + 类型 + 目标双版本」，上下文聚焦，不偏差 |
| 合并 | 每个 Issue 只影响一个模块或一个 agent 的版本线，**冲突面收敛、合并不失效** |
| 持续开发 | 新 Issue 通过 `depends_on` 挂到对应维度版本线上，可随时接着加强 |
| 观测/决策 | 双版本演进线即「模块能力看板 + agent 能力看板」，人类可俯瞰各自演进 |

## 二、核心概念

### 1. 两个版本维度（双版本，互不抢号）

| 维度 | 字段 | 作用对象 | 独立演进 |
|------|------|----------|----------|
| 模块版本 | `module_version` | 模块（`arch-skill`/`multirole`/`knowledge`/`dashboard`/`testing`/`pipeline`/`issue-mgmt`/`framework`…） | ✅ 每次升一个模块 |
| agent 版本 | `agent_version` | agent 角色（`架构·总师`/`架构·产品`/`架构·开发`/`架构·评审`/`架构·测试`…） | ✅ 每次升一个角色 |

一个 Issue 可以：
- **只动模块** → 只写 `module_version`；
- **只动 agent** → 只写 `agent` + `agent_version`；
- **模块与 agent 都动** → 两个维度都写、各升各的。

**核心原则：以较小的迭代单位推进。** 每个 Issue 的改动收敛在**单一模块或单一 agent** 的最小单位内，不跨维度强推整体版本，从而把并发合并的冲突概率降到最低。

### 2. Issue 声明头（front-matter，版本强制）

每个 Issue 顶部声明字段，把 Issue 锚定到某模块/某 agent 的某个版本目标上：

```yaml
module:         <模块ID>
module_version: <目标模块版本>      # 必填（非 standalone）
agent:          <角色ID>           # 选填，涉及 agent 能力时必填
agent_version:  <目标 agent 版本>   # 填了 agent 则必填
type:           init|update|fix|standalone
target:         <本 issue 目标>
update:         <相对上一版本改了什么>
depends_on:     <父模块 issue / 前置 issue 编号>
```

### 3. Issue 类型（type）与版本动作

| type | 含义 | 版本动作（作用于对应维度） | 是否需版本管理 |
|------|------|---------------------------|----------------|
| `init` | 模块/agent 建立 / 首个版本 | 创建对应维度版本线根节点，`v0.1.0` | ✅ |
| `update` | 能力增强 / 阶段性迭代 | `MINOR` 升级（`v0.2.0`） | ✅ |
| `fix` | 缺陷修复 / 小改 | `PATCH` 升级（`v0.2.1`） | ✅ |
| `standalone` | 一次性任务 | 不改变能力 | ❌ |
| `upgrade` | **框架级自升级**（跨模块/方法论/治理/测试红线） | `MINOR` 升级（`v0.2.0`） | ✅（纳入 `framework` 模块版本线，见 docs/FRAMEWORK_UPGRADE.md） |

### 4. Issue 关系层级（双版本演进线）

Issue 不是同层散点，而是挂在「模块根 issue」和「agent 角色根 issue」下的演进树：

```
模块「arch-skill」版本线                 agent「架构·总师」版本线
    ├── #4  type=update mv0.2.0             ├── #5  type=update av0.3.0
    ├── #EX-1 type=fix  mv0.2.1             └── #EX-2 type=fix  av0.3.1
    └── #EX-3 type=update mv0.3.0

（上表 #4/#5 为真实 Issue，其余 `#EX-*` 均为示意编号，非真实 Issue）

#4 只动 arch-skill 模块 → 只升 module_version=mv0.2.0，不写 agent/agent_version；
#5 只动 架构·总师 agent → 只升 agent_version=av0.3.0，不写 module_version。
#4 与 #5 可并行开发、各自合并，不抢同一个"整体版本号"，局部迭代不会互相冲突。
```

## 三、与「接力卡」的关系（A 方案）

架构八步中需要分工协作时，架构师通过**接力卡**召唤协作角色。接力卡载体采用确认的 **A 方案：Issue 评论内嵌结构化卡片**。

- **Issue 本身**：承载「模块/agent 声明 + 双版本 + 目标」，是任务的**版本锚点**。
- **Issue 评论**：承载「接力卡」（任务书 + 当前进度 + 下一步），是协作的**上下文传递**。

```yaml
# 接力卡内嵌卡片（评论中）
[触发: <架构·产品/开发/评审/测试>]
任务书: <目标+边界+验收>
接手角色: <本卡交给谁，如 架构·开发>
输入上下文: <模块/agent/版本/前置产物>
当前进度: <已完成/卡点>
下一步: <待办>
输出契约: <该角色须交出的产物>
---
```

### 触发强制化与回转/打断

- **三层触发**：显式 `[触发]`（最高优先）/ 语义向量命中职责域 / `AGENTS.md` rules 固定兜底，协作角色被强制唤起而非靠自觉（详见 `SKILL.md`）。
- **回转（打回）**：下游不达标（评审 🔴必修 / 测试 🔴阻塞）评论内嵌 `[回转] 退回:<角色> / 原因 / 下一步要求` 打回；被打回方按下一步要求返工并交回下游复评，最多 3 次，超次标 `blocked`。
- **打断（中断续跑）**：中断发 `[打断]` 并留续跑点（`当前进度` 标已做到哪一步+卡点+下一步），续跑凭进度无缝接续，不重做已完成部分。
- 整条链路由 `tests/test_relay_workflow.sh`（T8）端到端可复现。

## 四、版本号规则（双维度语义化）

- 采用语义化版本 `vMAJOR.MINOR.PATCH`。
- `init` → `v0.1.0`；`update` → 升 `MINOR`；`fix` → 升 `PATCH`。
- **模块维度与 agent 维度各自独立升版**，互不干扰：
  - 只改模块 → 升 `module_version`；
  - 只改 agent → 升 `agent_version`；
  - 都改 → 两个都升。
- 同一维度并发 Issue 由版本号串联，**先到先合并**；若并发冲突，按版本线依次合，避免同版本覆盖。
- `standalone` 不占用版本号，不污染版本线。

## 五、可视化看板（双版本展示）

`scripts/generate-dashboard.py` 会解析每个 Issue 的 `module_version` 与 `agent_version`，自动生成：
- **模块版本演进看板**：每个模块一条版本线；
- **Agent 角色版本演进看板**：每个 agent 角色一条版本线；
- **冲突/迭代扫描**：标记"疑似跨维度强推整体版本 / 版本跳号 / 未写明版本"的 Issue，帮助人类提前发现合并冲突风险。

人类俯瞰直接看 [docs/DASHBOARD.md](DASHBOARD.md)。

## 七、解耦式功能模块开发（按功能分布 · base 一律 main）

双版本管理解决「版本归属与演进」，还需解决「模块之间/分支之间的**耦合**」。每个功能模块必须**解耦开发、按功能分布**（详见 AGENTS.md「解耦式功能模块开发」固定规则）：

- **每个模块独立成 PR，base 一律 `main`**，禁止把新功能模块 base 挂到另一个功能分支/集成分支上（如 `auto/architect-framework-*`）。挂在功能分支上会与该分支耦合，别人一动就冲突（#29/#30 教训）。
- **按功能域解耦**：模块间只通过稳定接口/数据契约交互，不互相 import 实现、不共享私有内部状态；跨项目可独立抽取复用。
- **接口显式化**：模块对外能力收口到显式公开接口（`__init__.py` 导出 + docstring + 单测），便于跨项目调用与参考；接口变更须升版留痕。
- **冲突前置规避**：开 PR 前本地 `merge-tree` 校验与 `main` 无冲突，有冲突先 `rebase main` 解决再提，禁止带着 conflict 提 PR。
- **每个 PR 自含测试 + 文档**：模块自己的 `test_*.sh`/单测 + `docs/<MODULE>.md`，独立通过信号灯。

> 评审在 PR 层面核验五条（base 是 main / 按功能域独立 / 接口显式 / 无冲突 / 自带测试文档），任一不满足即打回。

## 八、对本框架的意义

- 让「模块化、可独立演进」理念**落地到 Issue 管理粒度**：模块与 agent 各自拥有独立版本线，能力可被多次阶段性加强。
- 让人类观察者的「二级信息」多两个维度：**模块能力看板 + agent 能力看板**。
- 让架构师 / 开发 / 评审 / 测试的上下文**有明确的版本锚点**，杜绝「改的是哪一版」的混乱。
- **以较小的迭代单位推进，杜绝"局部迭代强推整体版本"导致的合并失效**——每个 Issue 只在一个最小维度上前进，合并面收敛、冲突可控、可并行。
