# 专家级架构能力 · EXPERT_ARCHITECT

> **定位**：本文件是「通用架构师为什么够专家级」的方法论正文。机器可执行的规范在
> `local-agent/expertise/spec.py`（**唯一事实源**），本文件负责**说清判据与理由**。
> 若判据变更：先改 spec.py，再回来刷本文件与 `docs/CAPABILITY_INDEX.md`（防索引漂移）。

## 一、为什么需要这一层（问题陈述）

旧形态的「通用架构师」有一个结构性缺陷：**它把「通用」误解成「全能」**。
一个 agent 被要求设计任何行业的方案，它只能靠模型参数里的模糊印象作答 ——
既不知道律所与电商的作业流程差异，也不知道当前 AI 到底能不能解决这个问题。
结果是：产出看起来很完整，但**判断不可信**，且**无法被证伪**。

专家级架构师的做法是把「全能」拆成**四个可验证的来源**，缺一个都不成立：

| 支柱 | 回答的问题 | 事实源 | 落地 |
|---|---|---|---|
| ① 行业/岗位专家层 | 这个行业、这个岗位**实际怎么做**？ | `hanghangchuzhuangyuan` 注册表 | `expertise/experts.py` |
| ② AI 能力前沿层 | 当前 AI 能做什么、**下一步**能解决什么？ | `data/ai-frontier.yaml` | `expertise/ai_frontier.py` |
| ③ 帕累托前沿 | 多个备选里，**为什么选这个**？ | 调用方给出的备选（≥2） | `expertise/pareto.py` |
| ④ 外部验证门禁 | 凭什么相信它**真的能用**？ | **真实执行过的**功能性验证 | `expertise/external_validation.py` |

另有贯穿全部四者的 **时效性闸门**（`expertise/freshness.py`）：陈旧信息不得作为决策依据。

> 一句话：**专家级 = 有来源 + 有比较 + 有验证 + 有时间。**
> 任何一条缺失，判定必须显式降级，**不许默认通过**。

## 二、七维评判（DIMENSION_SPECS · 唯一事实源）

每个架构判断都必须回答下面七个问题。**七维全部必过**（`required=True`），
缺任何一维 → `inadmissible`（不准入），无论其它维度多高。

| # | 维度 | 必须回答的问题 | 权重 | 可接受证据 |
|---|---|---|---|---|
| 1 | **高度** | 站在什么目标层级？服务业务北极星还是局部需求？ | 0.15 | 目标层级声明 / 北极星指标 / 战略对齐 |
| 2 | **深度** | 关键决策的技术纵深够吗？边界、失败模式、不变量讲清了吗？ | 0.15 | 模块边界与依赖 / 失败模式与降级 / 不变量 |
| 3 | **广度** | 跨行业/跨岗位/跨模块的覆盖与复用考虑到了吗？ | 0.12 | 专家层命中 / 跨域复用与契约 / 横向对照 |
| 4 | **资源** | 成本、人力、时间、算力被量化了吗？ | 0.12 | 成本估算 / 人力工期 / 算力预算上限 |
| 5 | **实现路径** | 从现状到目标的分步路径明确吗？有里程碑与回退点吗？ | 0.13 | 阶段划分 / 里程碑验收 / 回退降级点 |
| 6 | **帕累托最优** | 备选方案显式比较了吗？取舍说清了吗？ | 0.13 | 候选≥2 / 多目标对比 / 前沿与支配关系 |
| 7 | **外部验证** | 外部独立证据通过了吗？**功能性代码验证**跑通了吗？ | 0.20 | 真实执行结果 / 第三方复核 / CI 红绿 |

权重和为 1.0（`spec.validate_specs()` 自检，权重被改坏即红灯）。
**外部验证权重最高（0.20）**，因为它是唯一能证伪结论的一维。

### 分档（JUDGE_THRESHOLDS）

| 档位 | 条件 |
|---|---|
| `inadmissible` | 七维有缺失 或 时效性闸门未过 → **不准入** |
| `expert` | 准入且加权得分 ≥ 0.85 且无弱维 → 专家级 |
| `competent` | 准入且得分 ≥ 0.70 → 合格但不称专家级 |
| `insufficient` | 准入但得分 < 0.70 → 不足以支撑决策 |

> 判不出来（读不到专家层 / 无法执行验证 / 证据无日期）一律 `unknown` / `inadmissible`，
> **不静默转成通过**（遵循 AGENTS.md 唯一事实纪律「判不出来 ≠ 通过」）。

## 三、外部验证：只认「真实执行过的功能性验证」

这是本体系与「嘴上说测过了」的分界线。

### 3.1 什么算功能性验证

| 类型 | 例子 | 算功能验证？ |
|---|---|---|
| **功能性（行为级）** | `pytest` / `python xxx.py` / `node x.js` / `bash test.sh` / `curl` / `npm run build` | ✅ 算 |
| **静态检查** | `grep` / `find` / `cat` / `test -f` / `diff` / `wc -l` | ❌ **不算**（只证明长得像，不证明能跑） |
| 混合命令 | `sh -c "grep x && python y"` | ⚠️ 判 `unknown`，要求拆开 |

### 3.2 证据五要素（缺一即不可信）

`external_validation.verify_claim()` 核验一份验证声明时，**只认下面真实产生的字段**，
调用方自填的 `verified: true` 一律忽略：

1. `command` —— 非空，且被判为功能性；
2. `status == "pass"`；
3. `exit_code` —— 有真实退出码（证明跑过）；
4. `output_digest` / `output_summary` —— 有真实输出（证明有行为）；
5. `executed_at` —— 真实时间，**不能在未来**，且未超过 `max_age_days`（默认 30 天）。

**反造假清单**（全部有测试覆盖）：静态冒充、失败命令、超时、未来时间戳、
自述"已验证"但无执行证据、空证据集（判 `unknown`）。

### 3.3 用法

```python
from expertise import run_check, validation_gate, evaluate

ev = run_check("python3 -m pytest tests/test_expertise.py -q")   # 真实执行
gate = validation_gate([ev])                                     # 门禁聚合
verdict = evaluate({"dimensions": {...}, "claims": [ev], "facts": [...]})
```

## 四、帕累托前沿：把「选型」变成可解释的取舍

### 4.1 判定规则

- 多目标、每目标带方向（`max`/`min`）；
- **支配**：目标集合**完全一致**，且所有目标不劣、至少一个严格更优；
- **前沿**：互不支配的候选集合（第 1 层）；
- **候选 < 2 → 判定不可信**（没有备选就没有前沿）。

### 4.2 一个必须说清的设计取舍

早期实现允许「部分目标重叠」即判定支配，导致 A（报了 2 个目标）去支配 D（报了 3 个目标），
把 D 错误地踢出前沿 —— **这是用一个不完整的目标集下断言**。
现实现要求**目标集合完全一致**才可比；跨签名的候选**一律互不支配**，都留在前沿上交给人与更多证据判断。
理由：宁可把不可比的方案都保留（显式暴露不确定性），也不许静默淘汰一个方案。

### 4.3 输出

`evaluate()` 返回 `frontier`（前沿）、`layers`（帕累托分层）、
`dominated`（谁被谁支配）、`choice`（选定点）、`explanation`（人可读解释）。
若调用方指定的 `preferred` 不在前沿上 → 该维判 weak（取舍不自洽）。

## 五、AI 能力前沿：能力边界是时间相关的

`data/ai-frontier.yaml` 每条能力声明必须带：

- `state`：`frontier`（前沿可达）/ `mainstream`（主流可靠）/ `commodity`（商品化便宜）/
  `emerging`（萌芽，风险高）/ `blocked`（当前不可行，须写原因）；
- `dated_at` + `source`：**时效硬约束**；
- `next_problem`：**下一步能解决什么问题**（这是"往前看"的部分，不是现状复述）。

`AIFrontier.capability_at(name)` 判定 `verdict`：
`feasible` / `risky` / `blocked` / `unverified`。
**声明一旦超出时效（AI 模型类 30 天）即降级为 `unverified`** —— 陈旧能力不得支撑"能做"的结论。
未收录的能力一律 `unknown`，**不得默认"能做"**。

> 维护纪律：季度整体复核；`ai_model` / `ai_framework` 类条目 30~60 天逐条复核并更新
> `dated_at` 与 `source`。复核不动 = 能力声明静默失效（系统会判 unverified，但没人更新就没价值）。

## 六、信息时效性：陈旧 ≠ 可信

| 信息类型 | 上限 | 理由 |
|---|---|---|
| AI 模型 | 30 天 | 能力/价格/上下文窗口变化极快 |
| AI 框架/API | 60 天 | 契约半年内常破坏性变更 |
| AI 研究/论文 | 180 天 | 需看是否被新结果推翻 |
| 行业做法/岗位流程 | 365 天 | 相对稳定，但必须带样本来源与年份 |
| 法规政策 | 365 天 | 须注明生效日期与地域 |
| 价格/成本 | 30 天 | 不得用缓存价做决策 |
| 榜单/基准 | 90 天 | 会被新模型刷新 |
| 内部决策 | 不按天数 | 以 ADR 版本为准，被 Superseded 即失效 |

四档判定：`fresh` / `ageing`（可用须标注）/ `stale`（不可用）/ `undated`（无日期 = 不可信）/ `unknown`（读不到）。
**缺少 `source` 的事实，即使新鲜也不得作为决策依据。**

## 七、接入方式

本能力作为**通用能力**挂载到角色层（与 DispatchAbility / DepthAbility 同构），
任何角色都可调用，不各自实现：

```python
from roles.architect import ArchitectRole
arch = ArchitectRole()
arch.assess_expertise({...})   # → 七维 verdict
arch.resolve_industry("给律所做合同审查系统")   # → 行业/岗位专家判定
arch.ai_frontier_at("多智能体协作编排")          # → 能力前沿状态
```

## 八、已知边界（不掩饰）

1. **专家层依赖外部仓库本地副本**：`hanghangchuzhuangyuan` 不在时显式降级为 `unverified`，
   不伪造命中。跨机器须设 `EXPERT_LAYER_ROOT`。
2. **AI 前沿数据靠人工维护**：`dated_at` 不自动更新，属 `emerging` 风险项，已在注册表内自标。
3. **行业覆盖仅 14 单元**：未覆盖行业的判定为 `no_match` → 必须走"补单元"而非硬凑。
4. **外部验证依赖命令可执行**：环境缺依赖时判 `fail`/`skipped`，不会假装通过。

## 九、测试信号灯

`local-agent/tests/test_expertise.sh`（8 组，真实执行）：

| 组 | 验证内容 |
|---|---|
| E1 | 七维规范自洽（权重和 / 全部必过 / 分档有序） |
| E2 | 专家层真实命中 + 无关需求不硬凑 |
| **E2b** | **专家层缺失时显式降级 `unverified`**（模拟云 CI 容器无外部仓副本；不崩溃、不伪造命中） |
| E3 | 帕累托支配/分层/min 方向/候选不足判不可信 |
| E4 | **真实跑子进程**：静态冒充/失败/超时/伪造/自述全被拦 |
| E5 | 时效性四档 + 空集不通过 |
| E6 | 自述验证/缺维/陈旧事实 均不能放行 |
| E7 | 陈旧能力声明降级 unverified，未收录判 unknown |
| E8 | Issue 唯一标题契约（幂等/收并/低信号拦截/正文契约） |

运行：`bash local-agent/tests/test_expertise.sh`（9 组）
（Windows 下若 bash 指向 WSL 解释器，用 `PYTHON=/mnt/d/.../python.exe` 指定本机解释器。）

> **CI 环境差异说明**：云 CI 容器（`python:3.11`）里**没有** `hanghangchuzhuangyuan` 副本，
> 因此 E2 在 CI 中走的是 E2b 的降级分支（判 `unverified`），而非真实命中 —— 这是**预期行为**，
> 不是"CI 没测到"。真实命中在本地/验收环境（有该仓副本）验证。
> 若要在 CI 里也做真实命中，需先把该仓副本检出到 `EXPERT_LAYER_ROOT` 指定路径。
