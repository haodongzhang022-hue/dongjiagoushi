# ADR-0012：跨角色链条走「阶段链门控」，不让本该串行的环节并行/重复触发

- 状态：Accepted
- 决策日期：2026-09
- 相关：Issue #150（打断补齐 · review-cycle v0.3.0）、`docs/REVIEW_EFFICIENCY.md` §二.④、ADR-0011

## 背景
ADR-0011 解决了"评审循环有多贵"（复述/构建/重复三类损耗）。但用户随后指认了**另一类更靠前的病**：

> 「我们还在处理开发的时候，他就又在跑测试了，然后之后又触发了评审，但是这场开发还没完成，
> 也就是说中间本该以链条进行，往后运行的他一次触发了。开发和测试就乱了。
> 导致重复触发也会导致进度失衡。」

即：**跨角色的链条没有被门控**——测试/评审的触发不校验上游开发是否已收口，
于是同一条链被"一次触发"多点并发（抢跑），同一阶段被重复触发，进度基准被稀释（失衡）。
这类损耗不是"贵"，而是**乱**：它破坏的是链条语义与进度可信度。

## 决策
为「开发 → 测试 → 评审」引入**阶段链门控**（`review_cycle/stage_spec.py` 唯一事实源 +
`review_cycle/gate.py` 确定性引擎），把"一次触发多点并发"改回**链式有序推进**：

- **单一活跃阶段**：同一任务任一时刻只承认一个活跃阶段（阶段活动登记表裁定），
  **上游未收口不许抢跑**；本阶段已在跑 = 重复触发 → **复用进行中的任务**（不新起、不冲进度）。
- **四类确定性判决**：`allow` / `blocked_active`（重复触发）/ `blocked_upstream`（抢跑）/
  `blocked_switched`（乱序）。全部由代码给定输入必得同一判决，不让 LLM 决定"现在该谁跑"。
- **驳回即零构建**：被驳回时不起任何构建（`dispatched=False`），且**不得给假绿放行标签**
  （统一映射到规范处置 `proceed` = "按序继续推进"，不是终局）。
- **`force` 显式逃生门**：确实要抢跑/复用时可显式绕过，但判决留痕 `forced=True`，**不静默绕过**。
- **静默接管**：阶段活动登记带超时（默认 1800s，可环境变量覆盖）——打标残留不会被永久当作
  "在跑"卡死整条链。
- **留痕与口径**：每次判决写 `archives(kind='stage_gate')`；`blocked_retriggers` =
  被拦下的乱触发总数，是"进度是否失衡"的可核验口径。

备选方案（未选）：
- 只靠"人/AI 记得按顺序" → 无门控判据、无留痕，正是当前痛点，不做；
- 让 LLM 判断"现在该谁跑" → 不确定、不可复现，违背"确定性状态机"既有纪律；
- 把阶段门与 DevTeam 合并 → DevTeam 管**小组内**执行-验证闭环，阶段门管**跨角色**链条先后，
  职责不同、合并会耦合（ADR-0005 解耦原则）。

## 后果（权衡）
- 好处：链条语义恢复、进度基准可信（`blocked_retriggers` 可核验）；抢跑/重复/乱序一律**零构建**，
  与 ADR-0011 的省 CPU 目标同向；确定性判决可测（9 组信号灯含专门两组）。
- 代价：门控引入**一次状态登记**（本地 JSON，可环境变量隔离）；阶段活动登记若长期不刷新会被
  静默接管（视为收口）——这与"防卡死"是一体两面，需调用方在阶段开工/收口时显式登记。
- 难反转：一旦流程按阶段链组织，回到"无门控并行触发"会重新引入乱序与进度失衡，故记 ADR。
