# ADR-0011：评审循环走「增量上下文 + 攒批异步」，不做同步乒乓式逐轮复述/构建

- 状态：Accepted
- 决策日期：2026-09
- 相关：Issue #150（review-context v0.2.0 / review-cycle v0.2.0）、`docs/REVIEW_EFFICIENCY.md`

## 背景
用户在 Issue #150 指认三个乘性放大的损耗：**每次评审复述整个大项目非常困难**、
**跑测试非常困难**、**「触发评审→跑开发→评审」效率慢且触发大量 CPU 构建/CPU 开发损耗**。

现状是**同步乒乓**：每轮评审一条评论就唤醒一次开发 + 拉起一次构建，一次冷启动摊不到任何东西；
稳定骨架（目标/边界/验收/契约/决策）每轮重算、重讲；同一份变更被多轮反复跑。

## 决策
把评审循环从「同步乒乓」改为「**增量上下文 + 攒批异步**」，落地为两个新模块 + 既有 Bus 增强：

- **增量上下文（`review_context`）**：稳定骨架构建一次即**冻结**，评审每轮只吃
  (冻结骨架摘要 + 本轮变化)；**内容指纹**是"骨架何时失效"的唯一判据，不做主观判断。
- **攒批异步（`review_cycle` + `hybrid.bus` 去重门）**：受影响测试**入列 0 成本**，
  一次发车**一个批次计划在同一构建内跑完**（N 次冷启动 → 1 次）；**同一变更指纹已发过车
  则直接拦截**，同 diff 永不重复触发构建；评审段用**确定性状态机 + 触发门控**驱动，不让 LLM 决定下一步。
- **接线进主流程**：`ReviewerRole.do_review` 内前置接线（可关可降级），
  与既有「双轴必走 + 统一处置标签」契约**并存不改**；`review-metrics` 度量有效性、本机制度量成本，正交。

备选方案（未选）：
- 只做 LLM 前缀缓存 → 治不了"评审**上下文文本**逐轮复述"与"每轮一次构建"，缓存作用在调用层而非编排层；
- 只把测试挪本地 → 治不了"轮次 N 倍放大构建次数"与"同 diff 重复触发"；
- 把评审改成"一次评完不迭代" → 会牺牲"以测试为准、复评清零"的既有质量闸门，不能为了省 CPU 降质量。

## 后果（权衡）
- 好处：三种损耗都有确定性口径可核验（`saved_ratio` / `cold_start_saved` / `avoided_builds` /
  `reused_rounds`），并可直接俯瞰（`--review-cycle stats`、控制页 `/review-cycle`）；
  主流程接线不改双轴/处置契约，回归风险可控；模块解耦、跨项目可抽取。
- 代价：**攒批意味着"延迟"**——测试不再即时跑，要等发车窗口（Bus 默认 15 分钟班次）；
  评审在"攒批未发车"期间只能拿到"待跑"状态。取舍取舍的是**CPU 成本**，代价是**反馈时延**；
  需要即时结论时用 `force=True` 或 `flush=True` 显式发车绕过攒批（逃生门已留）。
- 难反转：一旦各流程都按"增量上下文 + 攒批"组织，回到逐轮全量复述会重新引入乘性浪费，故记 ADR。
