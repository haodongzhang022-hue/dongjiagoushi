# ADR-0015：模型按「三档语义」配置，且降级必须显性

- 状态：Accepted
- 决策日期：2026-10
- 相关：Issue #147 / #182、PR #184 / #185、`docs/MODEL_ROUTING.md`

## 背景

用户要「快的怎么做」，但**快的标准不唯一**：有的角色要模型强、有的要回合快；
真实快档 ID（`deepseek-v4.1-flash-1017` / `minimax-3.1-flash`）还没在平台侧验真。
若只写「主档 + 备用 + 兜底」三串模型名，后人看不懂哪档是「指定」、哪档只是「随大流」；
更糟的是降级发生在路由内部，调用方只拿到最终文本，**换了模型没人知道**——
最难查的 bug 不是失败，是「它安静地用了别的模型，表现得像成功」。

## 决策

1. 渠道链按**三档语义**解读，而不是按位置猜：`fast`（该角色显式指定的首档）/
   `same`（与通用链同名，即「和其他角色一样」）/ `last_resort`（`last_resort_model`）。
   判据确定性：是否 `specified` + 成员是否在 `fallback_chain`。
2. 档3 单列为顶层 `last_resort_model`：`npc:go` 只接受单个 model 字段，平台上
   一定跑得起来的那一道必须显式存在，不能靠「链的最后一个」隐式承担。
3. **降级显性**：每跳写 `degraded/fallback_from/next`，降级成功补写 `model.call.degraded`，
   结果与后端 `last_degraded` 标出来源档→实际档，并打 warning。审计加
   `no_degrade_target`：链里没有「和其他角色一样」的档位就报红（单档链＝把静默失败写进配置）。

## 后果（权衡）

- 好处：快档「能不能用、降没降、降到哪」全线可读，不再靠事后翻日志猜；真实快档 ID
  确认后只改一处（`roles[角色].chain[0]` + `alias`）即全局生效。
- 代价：配置多一层语义（`tiers`），读的人要知道「链首=指定」这条约定；
  降级多写两条留痕（成本可忽略，换来可排查性）。
- 附带修掉一个真 bug：`openai_compat` 构造每档 caller 时闭包捕获循环变量，
  导致降级每一档实际都在调链尾模型（`calls == ['codebuddy'] * 3`）。已改为逐个绑定，
  并由信号灯断言「真的换了模型」——这类错不显性化就永远查不出来。
