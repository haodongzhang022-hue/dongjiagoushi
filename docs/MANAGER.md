# 经理与小组长：从「会表态」到「会干活」（Issue #239）

> 一句话：经理的产出不是一张分工表，是**平台上的任务 Issue + 真实接单回执 + 进度尺**。
> 小组长的产出不是再拆一张表，是**带组做完、客观验证过、整合交付了**。

---

## 一、病根（用户原话钉在墙上）

> 「会假装分工，实际上不激活其他 issue……只声明分工，相当于经理只原地当嘴，不及格。」
> 「只有一条路，计划都给他了，要求他推进度，他会纠结要不要按计划走……原地纠结要不要做。」
> 「他看起来不知道自己职责是什么。」
> 「可能小组长也不及格。不然他调配小组长也应该能完成，一起优化。」

三条症状，三条病根：

| 症状 | 病根 | 本质 |
|------|------|------|
| 假装分工、不激活 | 规划和执行之间**没接线** | 引擎早就存在（`dispatch_engine` L1→L4），但经理节点只 `llm.call()` 出段文字就返回 |
| 给了计划还纠结 | **没有"计划即命令"的判定** | "要不要做"被留给 LLM 自由发挥，于是它真的会纠结 |
| 不知道职责 | **越界没有代价** | 没有硬表、没有拦截，做什么都"看起来合理" |
| 小组长不合格 | 中间层**只拆不带队** | 经理把活交下来，小组长再出一张子任务表，活断在这层 |

**关键判断**：这不是"提示词写得不够好"的问题。上一版 settings.yml 里经理的 prompt
已经写满了「L4 才算完成」「无回执不算完成」——写得都对，但他还是只当嘴。
**靠自觉不行，得靠代码判定。**

---

## 二、修复：三个确定性机制

实现在 `local-agent/manager/`（不是提示词，是可执行的代码）。

### ① ACTIVATE 闸门 —— 只声明不算分工

`ManagerEngine.activate(plan)`：

- 计划 → `parse_plan()` 归一化为 assignment 清单（支持编号列表 / 逐行 / 结构化 dict）；
- 每条调 `dispatch_engine.dispatch()` 走 **L1 声明 → L2 分发 → L3 触发 → L4 开工**；
- 真实模式（有 repo + cnb 可用）下逐条**建任务 Issue**；
- **建不出 Issue 的任务一律标 `blocked_no_issue`**，绝不当已分工。

```python
m = ManagerEngine(repo="org/repo")
r = m.activate(plan)
# r["platform_activated"]  真正在平台激活了几条
# r["blocked_no_issue"]    几条建不出 Issue（等于没激活，必须显式暴露）
```

#### 🔴 顺手挖出的真实根因（比"嘴上不干活"更硬）

实测 `cnb issues create-issue` 发现：它的输出是 **YAML 风格文本**，不是纯 JSON，
且编号**带引号**：

```
status: 201
data:
  number: "242"
```

旧 `dispatch_engine._create_issue()` 只 `json.loads`，失败后退到
`int(val)` —— 而 `val` 是 `"242"`（带引号），`int('"242"')` 直接 `ValueError`，
于是**永远返回 `None`**。

后果：任何真实派发都被判 `platform_active=False` → `blocked_no_issue`。
**经理在真实环境里根本激活不出 Issue** —— 这不止是"他懒"，是**代码真的断在这**。

修复：抽出 `_parse_issue_number()`，YAML / JSON 两种格式 + 去引号统一处理，
`test_manager.sh` 第 11 组信号灯锁死（含「解析成功 → platform_activated=1」端到端断言）。

> 教训：**"他不干活"要先怀疑链路，再怀疑态度**。这次是链路。

### ② EXECUTE 闸门 —— 计划即命令，单路无抉择

`resolve_choice(options)` 是**纯函数查表**，三个返回值都不含"纠结"：

| 输入 | 决策 | 理由 |
|------|------|------|
| 单选项 | `EXECUTE` | 唯一路径，没有"要不要"这个分支 |
| 多选项 | `EXECUTE`（取首个，执行中纠偏） | 计划优先级优先 |
| 空 | `BLOCKED` | 没有路才该停，且必须显式说要什么 |

`execute_plan()` 是**唯一执行入口**：计划进来必然走完 激活→督促→监督，
中间不存在"要不要按计划走"的分支。

### ③ 职责硬表 + 越界拦截

`DUTIES` 写清经理只有四件事：**拆计划 / 真派发 / 督促落地 / 监督处置**。
`NOT_MANAGER` 列出所有不属于经理的动作及正确承接角色：

```
写代码 → 架构·开发    评审 → 架构·评审    跑测试 → 架构·测试
需求澄清 → 架构·产品  定架构 → 架构·总师  合并 → 架构·交付
```

`guard(action)` 命中即拦，并给出 `hand_to`（该派给谁）。

⚠️ **位置很重要**：越界校验针对「经理**自己要执行**的单个动作」；
计划进入 `execute_plan()` 即视为**派发意图**（计划里的"评审/测试"本来就是要派出去的），
一律走激活——不把派活误判成越界。

## 三、督促与监督：把"假装分工"揪出来

### 督促（`push`）

判据全部客观可查，不看经理"感觉"：

1. 查真实回执（`dispatch_verify`：progress 事件 `accepted`/`awake_ack`）；
2. 无回执 → **再唤醒一次**（投 `[触发:角色]` 接力卡）；
3. 仍无 → **调配小组长**（`delegate_to_lead`）：给出组内开发数、首动作、验收口径。

**活不掉地上**——这是经理"兜住"的意义，也是他不再"原地纠结"的原因：
不接单不是你该发愁的事，是你该转手的事。

### 监督（`supervise`）

| 判定 | 判据 | 处置 |
|------|------|------|
| `real` | 有回执 + 有开工/交付事件 | 放行 |
| `fake` | **回执了 `[接单]` 但无开工证据、无进度尺** | 转小组长落实 |
| `awaiting` | 无回执、无开工证据 | 转小组长落实 |
| `stall` | 连续 2 轮 `distance` 完全不变 | 哨兵 `[打断]` |
| `jump` | 最近 3 轮 `delta` 净进展 ≥ 0（来回打转不收敛） | 哨兵 `[打断]` |

`fake` 是本轮核心：**嘴上答应、手上不动**，这是"假装分工"最典型的形态，
上一版工具链完全抓不到，现在它必须现形。

## 四、小组长：接住中间层

`LeadEngine`（`local-agent/manager/lead_engine.py`），底层复用
`dev_team.DevTeamEngine`（Issue #74：确定性状态机 + 硬性熔断 + 进度北极星）。
**缺的从来不是引擎，是没人调用它**——所以 LeadEngine 是接线层，不是新造轮子。

| 环节 | 动作 | 判据 |
|------|------|------|
| 派 | `dispatch_devs(task)` 切成组内 N 片（默认 2），每人独立 gid | 每人有 gid 才叫派了 |
| 带 | `run_round(dev_outputs)` 执行 → **客观验证** → 决策 | 全部 APPROVED 才放行 |
| 收 | `aggregate()` 全通过 → 整合统一交付经理；超限 → 上报 | 有交付留痕才叫收 |

**四条铁律**：执行-验证分离（开发不自判合格）/ 一个没过就不放行 /
超 `max_attempts` 上报不无限重试 / 进度尺归小组自己盯。

## 五、角色接线（嘴接上手）

### 架构·经理（`roles/manager.py`）

| 入口 | 作用 |
|------|------|
| `manager_execute(plan)` | **首选**：计划 → 激活 → 督促 → 监督，一站式 |
| `manager_activate(plan)` | 只做真激活 |
| `manager_push()` | 只做督促 |
| `manager_supervise()` | 只做监督 + 处置 |
| `manager_status()` | 二级信息：谁真干了、谁停在嘴上 |
| `manager_guard(action)` | 职责校验 |

### 架构·小组长（`roles/team_lead.py`）

| 入口 | 作用 |
|------|------|
| `lead_dispatch_devs(task)` | 真派开发（组内 N 人各独立 gid） |
| `lead_run_round(...)` | 跑一轮确定性闭环 |
| `lead_aggregate()` | 整合交付 / 继续 / 上报 |
| `lead_drive(task, dev_outputs)` | 一站式：派 → 带 → 收 |
| `lead_overview()` | 本组俯瞰 |
| `group_convergence(group_id)` | 本组成员到目标的收敛俯瞰 |

两个角色的人设（`.cnb/settings.yml`）同步改成「三条铁律 + 四件事」，
`team.yaml` 加了 `engine:` 字段指向各自引擎。

## 六、与既有机制的关系（不重复造）

| 既有机制 | 关系 |
|----------|------|
| `DispatchAbility`（全员通用） | 经理复用它的 `dispatch()` / `dispatch_verify()` / `handoff_status()` |
| `dispatch_engine`（L1→L4） | ManagerEngine 的**执行底座**，不重写分发逻辑 |
| `dev_team` / `DevTeamAbility`（Issue #74） | LeadEngine 的**编排底座**，不重写小组状态机 |
| 监控哨兵（`sentinel.engine`） | 停滞/横跳交它按协议打断；进度尺口径同源 |
| 审核者前置助手（`resolve_choice` 同类问题） | 本模块的 `resolve_choice` 只负责**经理执行决策**，不替代 L1→L3 决策补全 |
| `docs/DISPATCH_DEPTH.md` | 四层深度模型的定义来源，本模块是其**执行侧的落地** |

## 七、验收标准（`local-agent/tests/test_manager.sh` 11 组信号灯（含 YAML 解析回归））

1. 计划即命令：单路 EXECUTE / 多路取首个 / 空 BLOCKED，无「纠结」出口；
2. ACTIVATE 闸门：计划 → 逐条激活（任务 gid + 承接角色），空计划显式拒绝；
3. 反假装：只回执 `[接单]` 没下文 → 判 `fake` → 转小组长；真开工判 `real` 不误伤；
4. 督促：无人接单 → 再唤醒 → 转小组长（含首动作 + 验收口径），混合场景诚实统计；
5. 监督：停滞/横跳由进度尺判定 → 哨兵打断；
6. 职责护栏：5 类越界动作被拦并指向正确角色；派活不被误判为越界；
7. 小组长带队：未全过不放行，全过才整合交付；
8. 小组长熔断：重做超限 ESCALATED 上报；
9. 角色接线：经理 6 入口 + 小组长 6 入口全部可调用并跑通；
10. 端到端：经理激活 3 条 → 无人接单 → 全部转小组长 → 3 条全部整合交付；
11. 激活断链回归：cnb CLI 的 YAML 输出（编号带引号）必须解析出编号，
    解析成功才给 `platform_activated=1`（真实环境不再恒判 blocked_no_issue）。
