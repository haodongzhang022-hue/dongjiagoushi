# 经理与小组长：从「会表态」到「会干活」，再到「承上启下」（Issue #239）

> **一轮**：经理的产出不是一张分工表，是**平台上的任务 Issue + 真实接单回执 + 进度尺**。
> 小组长的产出不是再拆一张表，是**带组做完、客观验证过、整合交付了**。
>
> **二轮（更根本）**：如果经理只会把上级计划分槽投交接卡，那架构师分完直接程序自动
> 发卡就行了——**这个岗位就不需要存在**。经理是**承上启下**：找进度、找通路、看反馈、
> 换方式、调人员、跨岗借人。四段缺一段即不及格（见 §八）。

---

## 一、病根（用户原话钉在墙上）

> 「会假装分工，实际上不激活其他 issue……只声明分工，相当于经理只原地当嘴，不及格。」
> 「只有一条路，计划都给他了，要求他推进度，他会纠结要不要按计划走……原地纠结要不要做。」
> 「他看起来不知道自己职责是什么。」
> 「可能小组长也不及格。不然他调配小组长也应该能完成，一起优化。」

三条症状，三条病根：

| 症状 | 病根 | 本质 |
|------|------|------|
| 假装分工、不激活 | 规划和执行之间**没接线** | 引擎早就存在（`dispatch_engine` L1→L4），但经理节点只 `llm.call()` 出段文字就返回 |
| 给了计划还纠结 | **没有"计划即命令"的判定** | "要不要做"被留给 LLM 自由发挥，于是它真的会纠结 |
| 不知道职责 | **越界没有代价** | 没有硬表、没有拦截，做什么都"看起来合理" |
| 小组长不合格 | 中间层**只拆不带队** | 经理把活交下来，小组长再出一张子任务表，活断在这层 |

**关键判断**：这不是"提示词写得不够好"的问题。上一版 settings.yml 里经理的 prompt
已经写满了「L4 才算完成」「无回执不算完成」——写得都对，但他还是只当嘴。
**靠自觉不行，得靠代码判定。**

## 二、修复：三个确定性机制

实现在 `local-agent/manager/`（不是提示词，是可执行的代码）。

### ① ACTIVATE 闸门 —— 只声明不算分工

`ManagerEngine.activate(plan)`：

- 计划 → `parse_plan()` 归一化为 assignment 清单（支持编号列表 / 逐行 / 结构化 dict）；
- 每条调 `dispatch_engine.dispatch()` 走 **L1 声明 → L2 分发 → L3 触发 → L4 开工**；
- 真实模式（有 repo + cnb 可用）下逐条**建任务 Issue**；
- **建不出 Issue 的任务一律标 `blocked_no_issue`**，绝不当已分工。

```python
m = ManagerEngine(repo="org/repo")
r = m.activate(plan)
# r["platform_activated"]  真正在平台激活了几条
# r["blocked_no_issue"]    几条建不出 Issue（等于没激活，必须显式暴露）
```

#### 🔴 顺手挖出的真实根因（比"嘴上不干活"更硬）

实测 `cnb issues create-issue` 发现：它的输出是 **YAML 风格文本**，不是纯 JSON，
且编号**带引号**：

```
status: 201
data:
  number: "242"
```

旧 `dispatch_engine._create_issue()` 只 `json.loads`，失败后退到
`int(val)` —— 而 `val` 是 `"242"`（带引号），`int('"242"')` 直接 `ValueError`，
于是**永远返回 `None`**。

后果：任何真实派发都被判 `platform_active=False` → `blocked_no_issue`。
**经理在真实环境里根本激活不出 Issue** —— 这不止是"他懒"，是**代码真的断在这**。

修复：抽出 `_parse_issue_number()`，YAML / JSON 两种格式 + 去引号统一处理，
`test_manager.sh` 第 11 组信号灯锁死（含「解析成功 → platform_activated=1」端到端断言）。

> 教训：**"他不干活"要先怀疑链路，再怀疑态度**。这次是链路。

### ② EXECUTE 闸门 —— 计划即命令，单路无抉择

`resolve_choice(options)` 是**纯函数查表**，三个返回值都不含"纠结"：

| 输入 | 决策 | 理由 |
|------|------|------|
| 单选项 | `EXECUTE` | 唯一路径，没有"要不要"这个分支 |
| 多选项 | `EXECUTE`（取首个，执行中纠偏） | 计划优先级优先 |
| 空 | `BLOCKED` | 没有路才该停，且必须显式说要什么 |

`execute_plan()` 是**唯一执行入口**：计划进来必然走完 激活→督促→监督，
中间不存在"要不要按计划走"的分支。

### ③ 职责硬表 + 越界拦截

`DUTIES` 写清经理只有四件事：**拆计划 / 真派发 / 督促落地 / 监督处置**。
`NOT_MANAGER` 列出所有不属于经理的动作及正确承接角色：

```
写代码 → 架构·开发    评审 → 架构·评审    跑测试 → 架构·测试
需求澄清 → 架构·产品  定架构 → 架构·总师  合并 → 架构·交付
```

`guard(action)` 命中即拦，并给出 `hand_to`（该派给谁）。

⚠️ **位置很重要**：越界校验针对「经理**自己要执行**的单个动作」；
计划进入 `execute_plan()` 即视为**派发意图**（计划里的"评审/测试"本来就是要派出去的），
一律走激活——不把派活误判成越界。

## 三、督促与监督：把"假装分工"揪出来

### 督促（`push`）

判据全部客观可查，不看经理"感觉"：

1. 查真实回执（`dispatch_verify`：progress 事件 `accepted`/`awake_ack`）；
2. 无回执 → **再唤醒一次**（投 `[触发:角色]` 接力卡）；
3. 仍无 → **调配小组长**（`delegate_to_lead`）：给出组内开发数、首动作、验收口径。

**活不掉地上**——这是经理"兜住"的意义，也是他不再"原地纠结"的原因：
不接单不是你该发愁的事，是你该转手的事。

### 监督（`supervise`）

| 判定 | 判据 | 处置 |
|------|------|------|
| `real` | 有回执 + 有开工/交付事件 | 放行 |
| `fake` | **回执了 `[接单]` 但无开工证据、无进度尺** | 转小组长落实 |
| `awaiting` | 无回执、无开工证据 | 转小组长落实 |
| `stall` | 连续 2 轮 `distance` 完全不变 | 哨兵 `[打断]` |
| `jump` | 最近 3 轮 `delta` 净进展 ≥ 0（来回打转不收敛） | 哨兵 `[打断]` |

`fake` 是本轮核心：**嘴上答应、手上不动**，这是"假装分工"最典型的形态，
上一版工具链完全抓不到，现在它必须现形。

## 四、小组长：接住中间层

`LeadEngine`（`local-agent/manager/lead_engine.py`），底层复用
`dev_team.DevTeamEngine`（Issue #74：确定性状态机 + 硬性熔断 + 进度北极星）。
**缺的从来不是引擎，是没人调用它**——所以 LeadEngine 是接线层，不是新造轮子。

| 环节 | 动作 | 判据 |
|------|------|------|
| 派 | `dispatch_devs(task)` 切成组内 N 片（默认 2），每人独立 gid | 每人有 gid 才叫派了 |
| 带 | `run_round(dev_outputs)` 执行 → **客观验证** → 决策 | 全部 APPROVED 才放行 |
| 收 | `aggregate()` 全通过 → 整合统一交付经理；超限 → 上报 | 有交付留痕才叫收 |

**四条铁律**：执行-验证分离（开发不自判合格）/ 一个没过就不放行 /
超 `max_attempts` 上报不无限重试 / 进度尺归小组自己盯。

## 五、角色接线（嘴接上手）

### 架构·经理（`roles/manager.py`）

| 入口 | 作用 |
|------|------|
| `manager_carry(plan)` | **首选（二轮）**：承上 → 行下 → 启下 → 反馈（多轮直到收敛或带证据上交） |
| `manager_lanes()` / `manager_try_lanes(role, handlers)` | 找通路：多路线穷举，一条断了换下一条 |
| `manager_authorize(action)` | 权责内自决判定（SELF 就必须自己干，不申请授权） |
| `manager_self_check()` | 六项自检：承上/行下/启下/反馈/找通路/自决 |
| `manager_execute(plan)` | 一站式：计划 → 激活 → 督促 → 监督 |
| `manager_activate(plan)` | 只做真激活 |
| `manager_push()` | 只做督促 |
| `manager_supervise()` | 只做监督 + 处置 |
| `manager_status()` | 二级信息：谁真干了、谁停在嘴上 |
| `manager_guard(action)` | 职责校验 |

### 架构·小组长（`roles/team_lead.py`）

| 入口 | 作用 |
|------|------|
| `lead_dispatch_devs(task)` | 真派开发（组内 N 人各独立 gid） |
| `lead_run_round(...)` | 跑一轮确定性闭环 |
| `lead_aggregate()` | 整合交付 / 继续 / 上报 |
| `lead_drive(task, dev_outputs)` | 一站式：派 → 带 → 收 |
| `lead_overview()` | 本组俯瞰 |
| `group_convergence(group_id)` | 本组成员到目标的收敛俯瞰 |
| `lead_escalate(task, tried, need)` | 卡点超本组能力 → **带证据**交回经理 |
| `lead_borrow(task_key, role)` | 组内无人承接 → 申请跨岗借角色 |

两个角色的人设（`.cnb/settings.yml`）同步改成「三条铁律 + 四件事」，
`team.yaml` 加了 `engine:` 字段指向各自引擎。

## 七、验收标准（`local-agent/tests/test_manager.sh` 43 组信号灯）

1. 计划即命令：单路 EXECUTE / 多路取首个 / 空 BLOCKED，无「纠结」出口；
2. ACTIVATE 闸门：计划 → 逐条激活（任务 gid + 承接角色），空计划显式拒绝；
3. 反假装：只回执 `[接单]` 没下文 → 判 `fake` → 转小组长；真开工判 `real` 不误伤；
4. 督促：无人接单 → 再唤醒 → 转小组长（含首动作 + 验收口径），混合场景诚实统计；
5. 监督：停滞/横跳由进度尺判定 → 哨兵打断；
6. 职责护栏：5 类越界动作被拦并指向正确角色；派活不被误判为越界；
7. 小组长带队：未全过不放行，全过才整合交付；
8. 小组长熔断：重做超限 ESCALATED 上报；
9. 角色接线：经理 6 入口 + 小组长 6 入口全部可调用并跑通；
10. 端到端：经理激活 3 条 → 无人接单 → 全部转小组长 → 3 条全部整合交付；
11. 激活断链回归：cnb CLI 的 YAML 输出（编号带引号）必须解析出编号，
    解析成功才给 `platform_activated=1`（真实环境不再恒判 blocked_no_issue）；
12. 承上段：北极星复述 + 计划翻译成可派项 + 裁掉项给理由与替代路线；
13. 找通路：一条断了换下一条、逐条留痕、全断才 hard；`@CodeBuddy` 在册；
14. 权责内自决：权责内 SELF / 不可逆·超成本·越界 HUMAN；
15. 启下升级梯：再唤醒 → 调小组长 → 加派 → 跨岗借角色 → 自己兜底（逐轮不重复）；
16. 反馈闭环：多轮换手段直到收敛；不收敛则带证据上交；**不假收敛**；
17. 小组长：带证据上交 + 跨岗借角色（接单 ≠ 使命完成）；
18. 角色接线：经理 5 个承上启下入口可调用，铁律含承上启下/自决/穷尽才上交；
19. 权责口径不误伤：11 类「换个说法」的找通路动作仍判 SELF（不因措辞翻成申请授权），
    6 类红线（扩容并发/预算/额度/合并/改架构/删数据）仍判 HUMAN，超成本口径单列；
20. 唤醒失败不是终点：`_fallback_lane()` 按序换通路（fullpath → codebuddy →
    direct_handle），逐条判就绪并记 `missing`，留 `lane_fallback` 痕；仍无人接则交
    小组长，不空等、不谎报；
21-37. 接线闸门 / 证据分级 / 借人台账（见 §九-§十一）；
38. 没写平台 → `local_only` / `platform_activated=0`，summary 说"平台真建 0/N"（§十二）；

## 八、承上启下：这个岗位到底该干什么（二轮 · Issue #239 用户评论）

### 8.1 用户把话说死了

> 「经理应该做的是承上启下，不是被安排了任务后挤牙膏，戳一戳动一动，那不算及格的经理。」
> 「架构师传达下来的任务，经理如果只分下去，那架构师分完了直接程序自动分槽位去
>   交接卡就行了，**这里经理岗位直接不需要存在了**，这就是刚性传达。」
> 「实际上经理是找进度 找通路，安排和看反馈，寻找能行得通的方式安排下去后看看效果
>   反馈，进一步调整，不够还能调整人员，**跨部门找角色过来帮忙都行**。」
> 「职责范围内的还在申请授权……经理角色当末端员工了，还是失职。」

三条判定，没有解释空间：

1. **只分槽投卡 ＝ 可被程序替代 ＝ 岗位失职**；
2. **一次不通就默认做不到 ＝ 没找过通路 ＝ 失职**（`@CodeBuddy` 也是一种通路）；
3. **职责范围内申请授权 ＝ 把自己当末端员工 ＝ 失职**。

### 8.2 四段活，缺一段即不及格

实现在 `local-agent/manager/flow.py`（`ManagerFlow`），入口 `manager_carry(plan)`。

| 段 | 名字 | 干什么 | 可核验输出 |
|----|------|--------|------------|
| ① | **承上** | 接住上级意图：复述**北极星** → 把方案**翻译**成可派项 → **裁掉不可执行项** | `north_star` / `items` / `dropped`（裁掉带理由 + 替代路线） |
| ② | **行下** | 真派发 + 按**成功标准**核验（`[接单]` 回执 **+** 开工/进度证据） | 每条任务的 `verdict` |
| ③ | **启下** | 派不动就调人：再唤醒 → 调小组长 → 加派 → **跨岗借角色** → 拆小 → 自己兜底 | `staffing` 动作清单（逐轮升级） |
| ④ | **反馈** | 效果回来看，不达标换手段再跑一轮，直到收敛或**带证据上交** | `rounds[]` / `escalated` / `tried` |

**为什么「承上」不是复述**：`translate()` 按原文重判角色线索——既无显式「角色: X」、
也无任何动作线索的空话（"这件事你们看着办"），一律裁入 `dropped` 并给
`alt_lane`（先按语义匹配角色，匹配不到由经理拆成更小的可派项）。
**原样下发是失职，默默丢也是失职。**

（这里有个坑：`parse_plan()` 的 `_infer_role()` 有兜底——认不出就落「架构·开发」。
不重判的话，空话会变成一条开发任务，看着像"分工了"。所以承上段按原文再判一次。）

**为什么「启下」是升级梯而不是建议清单**：`staffing_options(rounds)` 逐轮换手段——
第 1 轮再唤醒，第 2 轮调小组长，第 3 轮加派，第 4 轮跨岗借角色。**每轮换一个，
不是每轮重复同一个动作**（重复＝仍在挤牙膏）。

### 8.3 找通路：一条断了不是「做不到」

实现在 `local-agent/manager/lanes.py`（`LaneRouter`），入口 `manager_lanes()` /
`manager_try_lanes(role, handlers)`。

| 通路 | 说明 | 就绪条件（代码判，不靠感觉） |
|------|------|------------------------------|
| `platform` | 平台真建任务 Issue —— 最硬的留痕 | 有 repo + cnb 可用 |
| `fullpath` | 完整 `@org/repo(角色)` + `[触发:角色]` 接力卡 | 有 repo |
| `codebuddy` | **`@CodeBuddy` 兜底召唤**（用户点名：这条也是通路） | 无 |
| `direct_handle` | HandleAbility 解析的角色 @ 直呼，不写死角色名 | 解析出 handle |
| `lead` | 调配小组长（带编制承接） | 无 |
| `self` | 经理自己承接（不越界的那部分，最后兜底） | 无 |

`attempt()` 按序**真试**，每条成败都留痕（`lane_attempt` / `lane_skipped` /
`lane_exhausted`）；**全断**才判 hard 并带「试过哪几条、卡在哪」上交。
`skipped_no_handler` 会显式标注（不假装试过）。

⚠️ `self` 兜底仍受职责硬表约束：只承接拆解/组织/催办/整理，**不替开发写码、
不替评审下结论**。

**通路要真试，不是挑一条试完就收工。** 通道在**发送层**就失败时（`_reawake` 返回
`sent=False`），经理不能原地等，`_fallback_lane()` 立刻算出下一跳并逐条判就绪：

```
fullpath（完整 @org/repo(角色)）→ codebuddy（@CodeBuddy）→ direct_handle（直接召唤）
```

每条未就绪都记 `missing` 原因（不是「我觉得应该能」），结果写 `lane_fallback` 留痕，
任务继续交小组长落实 —— **不空等、不谎报**（`test_manager.sh` 第 20 组锁）。

### 8.4 权责内自决：别当末端员工

`authorize(action)` 是纯函数，治「职责范围内的还在申请授权」：

| 判定 | 包含什么 |
|------|----------|
| **SELF**（自己干，不申请） | 选通路、重试、再唤醒、调整安排、调配小组长、换角色承接、拆分任务、加派改派、催办、跨岗借人、自建 Issue、发接力卡、自己兜底 |
| **HUMAN**（才找人） | 不可逆（合并 / 关闭 Issue / 删数据）、超成本（花钱 / 扩容预算）、敏感（Token / 密钥）、越界（改需求边界 / 改架构方向） |

判 SELF 就必须自己干。**「要不要申请授权」这个疑问由代码消灭，不由嘴解释。**

**口径不能只看字面巧不巧。** 病根之一是同一个意思换个说法就翻成「要不要授权」——
「换方式」「换路线」「调整人员」和「换角色承接」「跨岗借人」是同一件事，必须同判 SELF
（近义说法已并入 `SELF_AUTHORITY`）；反过来「扩容到 500 并发」「预算上调」「提升额度」
这类**真超成本**仍必须 HUMAN，且超成本口径单列成 `HUMAN_AUTHORITY_EXTRA`，不与 SELF
表混写（避免"扩容"两字被误伤或漏判）。第 19 组信号灯双向锁死：11 类换说法仍自决、
6 类红线仍交人。

### 8.5 反馈闭环：不许假收敛

`carry()` 多轮循环：核验 → 不达标 → 换手段/换通路 → 再核验。停只有两种：

1. **全部达到成功标准**（有回执 + 有开工证据）；
2. **穷尽手段后带证据显式上交**：`escalate` 载荷含 `tried`（试过什么）/
   `unresolved`（哪条卡住、为什么）/ `need`（人类决定换目标/换资源/降范围）。

> 本轮顺手修掉一个**假收敛 bug**：第二轮起 `_re_activate()` 不重建 Issue、返回空
> `activated`，`supervise()` 拿到空列表就判「零条未达标」→ **谎报全部落地**。
> 现已回填原激活记录（issue/agent/task_id）保住监督对象。教训同上一轮：
> **「他看起来做完了」也要先怀疑链路。**

### 8.6 小组长承上启下的下半段

`TeamLeadRole` 补两个入口（`roles/team_lead.py`）：

- `lead_escalate(task, tried, need)` —— 卡点超本组能力时**带证据**交回经理
  （试过什么 / 缺什么 / 要谁来帮），不是发一句「无人承接」就交回；
- `lead_borrow(task_key, role)` —— 组内没人接得住，直接申请**跨岗借角色**
  （HandleAbility 解析目标角色 @ 格式，经理协调）。

**回 `[接单]` 只是开始**：换承接方式 → 带证据上交 → 申请借人，这三条是做不完时的
正确答案，不是「我接了但做不了」。

### 8.7 经理自检（给人类快速判定及格）

`manager_self_check()` 返回六项布尔：承上 / 行下 / 启下 / 反馈 / 找通路 / 自决。
四段（承上、行下、启下、反馈）任一为 `False` 即本轮不及格。

### 8.8 接线闸门：写在旁边 = 罢工（本轮的真正教训）

上一轮我把 `lanes.py`（多通路穷举 + 权责自决）写得很完整，第 13/14 组信号灯全绿，
汇报里写着"一条路不通就换下一条""职责范围内不再申请授权"。

**但 `carry()` 主流程从头到尾一次都没调用过它。** 用 `self_check()` 一照就现形：

```
找通路: false
自决:   false
```

启下那四个手段也一样：`requeue` 没真唤醒、`delegate_lead` 只生成了一个
`leader_plan` 字典却没唤醒小组长、`add_devs` 没加任何人、`borrow_role` 的 note 写着
"调用 HandleAbility 定位"而代码里一次都没调——**每轮换一个动作名，本质是原地不动**。

这正好就是用户说的「挤牙膏」「只当嘴」的代码形态：换了更好看的样子，没换实质。

现在接成真动作（第 21/22 组信号灯锁死）：

| 手段 | 上一版（动作名） | 现在（真动作 + 外部凭据） |
|------|------------------|---------------------------|
| `requeue` | 记一个名字 | `wake_role()` 多通路穷举，返回 `lane` + `msg_id` |
| `delegate_lead` | 只生成 plan 字典 | 生成 plan **并真唤醒小组长**（`lead_wake.ok`） |
| `add_devs` | 记一个名字 | `ops.apply_more_agents()` 真拆分支，拿到新 `agent_id` / `split_id` |
| `borrow_role` | note 里写"调用 HandleAbility" | **真调** HandleAbility 解析 `handle` 并真召唤 |
| `split` | 记一个名字 | `ops.split_task()` 真拆出子任务 gid |

每个动作还强制带 `authority`（先过权责判定，判 SELF 才执行）和 `executed`。
不可用通路显式标 `skipped_unready` + `missing` 原因，**"我觉得应该能"不算试过**。

> 一句话记下来：**单测能过，是因为单测只测了我想到的那条路。**
> 「功能写好了」和「主链路用上了」是两件事，第二件才算完成。

## 九、四轮：验的时候又摸到三处「还是嘴巴」（Issue #239）

用户上一轮的话是「实现好了」——所以我没做新功能，拿他给的尺子去量上一轮的成品。
量出来三处，**全都不在新功能里，在"怎么算干了"这条判据上**。

### 9.1 第一处：绿的其实是模拟器

`ManagerEngine` 有个 `simulate={"*": "accept"}` 参数，测试里用它让对端"回执"，
于是第 3、10 组信号灯全绿。可这条链在任何真实环境里**从没跑过**——
绿的是模拟器，不是经理。

现在把「证据」这件事分级（`manager/work.py` · `credential_of()`）：

| 等级 | 来源 | 算不算干活 |
|------|------|------------|
| `external` | 平台可核验（Issue 回执 / PR / CI） | ✅ |
| `role` | 承接方真回执 + 真写进度尺 | ✅ |
| `simulated` | 演练注入 | ❌ **明确不算** |
| `none` | 无证据 | ❌ |

`supervise()` 只认 `READY_LEVELS = ("role", "external")`。演练回执现在判 `fake`，
理由写「只有演练回执（simulated），没有真实承接方开工」。第 23 组信号灯锁死。

### 9.2 第二处：交给小组长 = 换了个承接主体，活还在原地

`delegate_to_lead()` 上一版返回一个 `leader_plan` 字典就结束了。**`LeadEngine` 从头到尾
没被调用过**——于是"调配小组长"实际等于"把活改个名字挂到小组长名下"。

现在 `drive=True`（默认）直接驱动小组长引擎：

```
派开发（N 个，各独立 gid） → 跑确定性闭环（客观验证） → 整合交付 / 超限上报
```

顺手挖出一个让小组根本没跑起来的 bug：`LeadEngine.dispatch_devs()` 把 `dev_id` 填成了
子任务键（`任务::dev0`），而 `DevTeamEngine.devs` 的键是 `dev0/dev1`——`run_round()`
一进来就抛「未知开发」。**小组长看起来"派了开发"，其实一轮都没跑。**

### 9.3 第三处：通路"就绪"是伪的

`lanes.readiness()` 用 `handle or role` 兜底，于是 `direct_handle` **永远 ready**，
哪怕一个 @ 都没解析出来；`@CodeBuddy` 写了 `needs: ()`，没有 repo 也判就绪。

现在：

- `codebuddy` 需要 `repo`（没有会话载体就投不出去，判 ready 等于假装试过）；
- `direct_handle` 只认**完整** `@org/repo(角色)`（`is_full_handle()`），角色名不算 handle。

整条链不通时，通路表会诚实地红一片，而不是全绿。第 25 组信号灯锁死。

### 9.4 四条配套

| 新增 | 作用 |
|------|------|
| `RoleWorkFace`（`manager/work.py`） | 承接方标准工作面：`accept/start/progress/deliver`，任何角色都能真上工 |
| `WorkerRegistry` | 经理按角色名取到会干活的承接方；`has(role)` 代码判"这人能不能干" |
| `BaseRole.work_face()` | 全员挂载：每个角色都交得出自己的工作面 |
| `ManagerRole.manager_workers()` | 一行装出团队承接方注册表（开发/评审/测试/小组长/交付） |

### 9.5 自检口径也跟着纠了一次

上一版 `self_check()` 要求「启下/找通路/自决」**本单必须出现**——可一次普通任务本来
就不需要把六个手段全用一遍，于是全绿的链路自检报 false，红的是自检口径本身。

现在：承上/行下/反馈（本单必须做）+ 启下/找通路/自决（本单做过 **或** 已具备即算），
`capability_ready` 里写明来源。第 27 组信号灯锁死。

### 9.6 验收

`local-agent/tests/test_manager.sh` **22 → 27 组全绿**，23-27 组专锁本轮：

| 25 | 无 repo/无 cnb 时平台·接力·@CodeBuddy 一律未就绪；handle 只认完整 @ |

> 是那个替经理回执的模拟器。

## 十、收尾轮：把「自己给自己作证」这件事也堵上（Issue #239 评论 · PR #324 合并后）

用户的话是「324 已经合并了，尝试收尾吧」。所以这轮**不加功能**，只做一件事：
拿前面几轮自己立的尺子，去量已经在 main 上的成品。

量出三处，全都在**「谁来证明他干了」**这条判据上。

### 10.1 第一处：借人写死了岗位，等于借不到人

`borrow_role()` 上一版硬写「架构·开发」：

```python
elif code == "borrow_role":
    borrow = self.engine.borrow_role("架构·开发", task_key=v["task_key"])
```

问题不在代码长短，在语义：**借人的场景恰恰是"这个岗接不住"**——接不住的那个岗
通常就是开发。于是"跨岗借角色"永远去借那个接不住的人，必失败，再回来报
「跨岗借不到」。手段齐全，动作全是空的。

现在借谁**从团队名册派生**：

- `roles.TEAM_ROSTER` / `roster_available()` 是单一事实源（`get_role` 能装载出实例的才算）；
- `borrow_candidates(exclude=..., task=...)` 排除本岗、排除经理自己，按任务文本相关度排序
  （任务提"评审"就先借评审）；
- `borrow_role("")` 留空即自动换人，返回 `candidates` 说明"本来还能借谁"。

`ManagerRole.manager_workers()` 也跟着改成名册派生——承接方不再只有那 5 个写死角色，
是 27 个在册角色。

### 10.2 第二处：回执和"开工"被当成了成果

旧判据里 `has_work` 看的是 `work_started`。可这条事件有两个脏来源：

| 来源 | 谁写的 | 能不能算承接方干了活 |
|------|--------|---------------------|
| 承接方真开工 | 承接方 | 算"动作"，但仍不是成果 |
| `dispatch_trigger` 补的开工 | **派发方自己**（投接力卡走 L3→L4 时会补一笔） | ❌ 根本不是承接方干的 |
| 演练投卡 | 演练 | ❌ |

于是出现过这种场面：对端只回了一句 `[接单]`，派发方一唤醒，库里就多了一条
`work_started`，监督一看 → `real`「真在推进」。**这是自己给自己作证。**

现在把"干了"的判据收紧成**成果**（`_produced_count()`）：

- 只认 `progressed` / `delivered`；`accepted`、`work_started` 一律不算；
- 停滞/横跳另用 `has_work and meters`（有开工 + 有刻度）判"卡住"——卡住比没回执更该抓；
- 凭据分级 `credential_of()` 同步收紧：`external` 也必须有推进/交付，光有 Issue 编号不够。

### 10.3 第三处：演练会往真任务上写别人的动作

`activate()` 走 `dispatch_engine.dispatch()`，那里面有 L3→L4：对已回执的任务会
补一笔 `work_started`。演练（`simulate`）也走这条路，于是**假的回执在真任务上留下了
一笔"开工"**，后面谁看这条任务都会以为对方动过手。

现在：

- `dispatch(..., trigger=False)` —— 演练不投卡、不开工，只登记；
- `activate()` 在 `simulate` 时自动传 `trigger=False`；
- `push()` 里**演练回执排在真唤醒之前**，演练完直接 `continue`，不叠加唤醒副产物。

一句话：**演练只能验证经理自己的链路，不许往真任务上记别人的动作。**

### 10.4 顺手把顺位纠正了

`_verdict()` 里原来的顺序是「先判凭据分级，再判停滞/横跳」。结果是：
有刻度、连续不推进的任务，被"演练不算干活"一句话盖成 `fake`，
"卡住"这个更该报警的信号反而看不到。现在**先判距离（停滞/横跳），再判凭据**。

### 10.5 验收

`local-agent/tests/test_manager.sh` **27 → 29 组全绿**，28/29 专锁本轮：

| 组 | 锁什么 |
|----|--------|
| 28 | 借人候选从名册派生（不写死开发）、按任务相关度排序、真解析 `@` 再召唤 |
| 29 | 驱动失败必须留痕不吞异常；监督判词不得与证据相悖；组内一轮未通过不放行 |

另加两份功能级证据脚本（`scripts/feature-verify/manager/`）：

- `借人从名册派生.sh` —— 候选与相关度来自名册，不是写死一个名字；
- `回执不是成果.sh` —— 只有回执 + 唤醒副产物时，必须不判 `real`。

`feature-verify --changed` **13 项全绿**；`local-agent/` 全量 **0 红**；
根 `tests/` 全量 **0 红**；文档一致性 **101/101**；`--check-map` 🟢。

> 这一轮的教训不是"又漏了什么功能"，是：**判据本身也会造假**。
> 「有回执」「有开工事件」「调用过 HandleAbility」——这些看着都像证据，
> 但它们全都可以由派发方自己制造。真正不能自造的只有两样：
> **别人写下的推进刻度**，和**别人跑出来的交付物**。

## 十一、按需借人 + 借人台账：把「重复找不到人用」这条死路堵上（Issue #239 收尾轮二）

上一轮（§十）把借人从"写死一个名字"改成"从名册派生"。方向对了，但**只解决了"能借谁"，
没解决"借过谁"**。用户这轮一句话点到了：

> 「借人改成按需，不再直接写死，尤其是记录一下是否成功，失败的话需要换其他的人，
>   他缺这一步结果的记录，会重复找不到人用。」

### 11.1 病灶：借失败没有记忆

改之前，`borrow_role()` 一圈跑完，结果只留在当次的返回值里。下一轮再借，仍然是从
名册第一个开始试起——**那个借不到的人被反复借、反复失败**，日志里堆一堆同样的无用人名，
真正的候选（名册后半截）一次都没试到。

看起来像"借不到人"，其实是**没有记忆**。这类缺陷最麻烦的地方在于：
每一轮都"试了"、每一步都"有动作"、日志也写出了人名，无从看出它是死的。

### 11.2 三件事：留痕、排除、换人

新增独立模块 `local-agent/manager/borrow.py`（借人台账），只做三件事：

| 事 | 怎么做 | 判据 |
|----|--------|------|
| **留痕** | 每次借人写 `borrow_ledger`（谁 / 哪条通路 / 成没成 / 为什么没成 / handle） | `record()` 可查，`overview()` 能俯瞰 |
| **排除** | 该任务上"最近一次仍失败"的人，不再自动重复借 | `failed_roles()` 由台账算出 |
| **换人** | 一次借不到试下一个；候选全败显式说"该换手段了" | `pick_candidates()` + `next` 结论 |

数据层配套：`borrow_ledger` 表（`schema.py` 第 34 张）+ `repo.add_borrow/list_borrows/
borrow_failed_roles`；`admin.record_borrow()` 顺带写一条 `progress`（`borrowed` /
`borrow_failed`），可回溯。

### 11.3 「借到人」的判据也收紧了

`wake.ok` 不等于借到人。唤醒结果里有两类**不是借人**的兜底：

| 通路 | 是不是借到人 |
|------|--------------|
| `platform` / `fullpath` / `codebuddy` / `direct_handle` | ✅ 卡真投给了被借的人 |
| `lead`（转小组长带编制） | ❌ 人是经理组里的，没跨岗 |
| `self`（经理自己顶上） | ❌ 根本没借 |

把 `self` 记成"借人成功"，就是又给自己作了一次证——和 §十 的 `work_started` 是同一个病。
`BORROWED_LANES` 是这条判据的唯一出处。

### 11.4 顺手挖出一个真 bug（被异常吞掉的降级）

写 `_borrow_once()` 时对了一遍 `HandleAbility` 的真实签名，发现上一版是：

```python
ha = HandleAbility(agent_name=self.owner, repo=self.repo)   # ← 签名对不上
```

`HandleAbility.__init__` 的入参是 `owner/at_str/current_org/current_repo`，
传 `agent_name=` 直接 `TypeError`，然后被 `except` 兜成"手写 @ 降级"。
**每次借人都在降级，而且看起来一切正常**——handle 里确实有 `@org/repo(角色)`，
只是那句 `borrow_role_resolve_failed` 没人看。

现在按真实签名传，解析失败才算降级并写进台账 `reason`。
教训跟 §十 一样：**吞掉的异常，就是下次判据造假的口子。**

### 11.5 接线：不只写在模块里

`ManagerFlow._apply_staffing()` 的 `borrow_role` 分支（启下第 4 档）现在带三项凭据：

- `action["borrow_recorded"]` —— 这次借人有没有落台账；
- `action["borrow"]["tried"]` —— 逐个候选的 `role/ok/reason`；
- `action["next_on_fail"]` —— 借不到时的下一步结论。

小组长侧 `lead_borrow()` 也改成按需 + 记台账：`role` 留空按任务语义派生；
指定的人若已经在这条任务上借败过，直接返回"台账在案，换下一个"，不再重复试。

角色层入口：`ManagerRole.manager_borrow()` / `manager_borrow_overview()`。

### 11.6 复评修正：把台账自己的窟窿堵上

上一版本轮 PR 被评审打回五处，都在**台账能不能自证**这一层：

| 病灶 | 为什么错 | 现在 |
|------|----------|------|
| `credential_of` 仍留 `len(real_events) >= 2` | `accepted + work_started` 这两笔**都能由派发方自己写**，凑条数就是把"自己给自己作证"放回来 | 只认 `committed`（`progressed`/`delivered`），`external` 也必须有成果 |
| `lead_borrow` 把"解析出 @"记成 `ok=1` | `lane="resolve"` 不在 `BORROWED_LANES`，却写了成功；台账最新一条被洗白 → `failed_roles()` 把人放回来，下轮重复借 | 真投接力卡才算借到；失败写清卡在哪，`lane` 只记真投出的通路 |
| `overview()` 与 `failed_roles()` 两套口径 | `history()` 新→旧，`last_ok` 循环结束留的是**最早一条**，先败后成的人被报成"仍借不到" | 按旧→新遍历，两者都取"最近一次" |
| `add_borrow()` 恒返回 `""` | `gen("borrow")` 生成后没保留，单条记录无法按 id 反查 | `bid = borrow_id or gen("borrow")`，写库与返回同值 |
| `_STALL_ROUNDS` 注释说"设为 1 的理由"但取值是 2 | 按注释改阈值的人会得到相反效果 | 注释改成"设为 2 的理由"，与取值一致 |

另外补两条同源口子：`lead_borrow` 留空按需派生时**没有排除台账里借败过的人**
（"按需"又从同一个人开始，这轮修的"重复找不到人用"等于白修）；`test_manager.sh` 里
`assert v2["event"] if False else True` 是恒真断言（等于没锁），改为真判"判 real 必须有
`progressed`/`delivered`"。

## 十二、五轮：口径不许替自己作证 —— 三档分明 + 真接线（Issue #239 五轮）

> 你说「继续，这几个处理了」。上一轮（#376）已经合进 `main`（`7693828`），
> `test_manager.sh` 37 组在干净 `main` 上全绿。所以这轮不加新功能——
> **拿前面几轮自己立的尺子，去量"已经合并、已经全绿"的成品。**

量出三处，全都在同一条缝上：**汇报的和发生的，不是一件事。**

### 12.1 报告「平台激活 N 条」，平台一条 Issue 都没有

```python
"platform_active": bool(issue_no) or self.dry_run,   # ← dry_run 下恒 True
```

`dry_run` 是"不碰平台"，却在这里被算成"平台激活"。于是实操长这样：

```
[经理引擎] 激活 2 条 / 平台激活 2 条 / blocked_no_issue=0
```

跑到仓库里看：**一条 Issue 都没有。**

这和 #342 的 `work_started` 是同一个病——**判据由自己制造，等于自己给自己开合格证**。
只是这次造的不是"开工"，是"激活"这个词本身。

现在三档分明，谁也别糊：

| 档 | 判据 | 算不算激活 |
|----|------|-----------|
| `platform_active` | 平台真建出 Issue 编号 | ✅ 真激活 |
| `local_only` | 只本地登记（task/agent gid 都在），没写平台 | ❌ 不算（但也不是失败） |
| `blocked_no_issue` | 该建却没建成（开了 live 却失败） | ❌ 等于没分工 |

summary 随之改成直白说：`平台真建 Issue 0/2 条任务；2 条只本地登记（没碰平台，不算激活）`。

**顺带加闸**：真建 Issue 是不可逆外部副作用（收尾轮一跑就刷了八十来个测试 Issue 还开着）。
现在默认**不写平台**，必须 `live=True` 或 `CNB_MANAGER_LIVE=1` 显式开。

### 12.2 仓库探测只认一个变量名，于是经理永远不碰平台

```python
self.repo = repo or os.environ.get("CNB_REPO") or ""   # ← 平台没这个变量
```

CNB 云端实际注入的是 `CNB_GROUP_SLUG` + `CNB_REPO_NAME`（还有 `CNB_REPO_SLUG`），
**没有 `CNB_REPO`**。于是 `repo` 恒空串 → `dry_run` 恒 True →
**经理在任何真实环境里都不会去建 Issue**，同时按上一条继续报"平台激活 N 条"。

两条错叠在一起，效果是：它看起来很忙，实际一步没走出去，而且每一句汇报都在替它作证。

现在 `repo` 语义收紧：

- `repo=None`（默认）= **去探测**：平台注入变量 → git remote；
  **不取 `detect_current_org_repo()` 的默认约定兜底**——默认值是"假设"，不是"探测到的"，
  把假设写成探测结果，跟"演练算干活"是同一个病。
- `repo=""` = 显式声明"没有仓库"（本地/离线）。

### 12.3 引擎及格 ≠ 流水线里那个经理及格

`orchestrator._run_role_engine` 里现造一个引擎：

```python
eng = ManagerEngine(devs_per_team=...)   # 没 repo、没 workers、不走 carry
res = eng.execute_plan(req)
```

三个后果一次全中：

| 缺什么 | 后果 |
|--------|------|
| 没 `repo` | 恒 `dry_run` → 平台一条都不建，还输出"平台激活" |
| `workers=None` | 启下「调人/借人/加派」全是空动作（九轮前的老病复发） |
| 走 `execute_plan` | 承上（裁不可执行）与反馈（多轮）根本没跑 |

单测全绿，是因为单测**直接调引擎**，绕开了流水线这条路。
所以「引擎及格」和「流水线里的经理及格」能长期共存——**测的位置比测的次数重要。**

现在复用角色自己的引擎（带 repo/owner/承接方）+ 走 `carry`，输出改成承上启下口径。

### 12.4 验收（`test_manager.sh` 37 → 41 组）

| 组 | 锁什么 |
|----|--------|
| 38 | 没写平台 → `local_only` / `platform_activated=0`；summary 说"平台真建 0/N"；真建成才 `activated` |
| 39 | 认平台真实注入变量（`GROUP_SLUG`+`REPO_NAME`）；`repo=""` 才是没仓库；`live` 需显式开 |
| 40 | 流水线经理节点：带 repo + 带承接方（27 个在册）+ 走 carry；输出不含旧措辞 |
| 41 | 真写平台要显式开：`CNB_MANAGER_LIVE` 未开时，有 repo 也不去写 |

功能级证据脚本新增 2 份（均已登记 `modules.map`）：

- `scripts/feature-verify/manager/平台激活不冒充.sh`——判"口径与事实是否一致"；
- `scripts/feature-verify/manager/经理节点真接线.sh`——判"真实调用链上那个经理是不是同一个"。

回归：`local-agent/` 全量 67 个脚本，除 `test_hybrid_pipeline.sh` / `test_topology_slim.sh`
（**干净 `main` 上同样红**，既有问题，未顺手改）外 0 红；根 `tests/` 18 个全绿；
文档一致性 101/101；`feature-verify --check-map` 🟢；`--module manager` **6/6** 绿。

> 这轮的教训：**"跑通了"要先问"跑的是哪儿"。**
>
> 直接调引擎能绿，流水线里的那个可能一次都没碰过平台；
> `platform_active` 能绿，因为它自己写自己；
> `repo` 探测能绿，因为它读到的是假设的默认值。
>
> 一句话——**能自己制造的绿灯，都不算证据。**

## 十三、六轮：判据写好了，但没接线（Issue #239 · 与五轮合并）

五轮修的是「口径替自己作证」，这轮量出的是另一种形态：**判据做对了，但从来没人调用它。**

### 13.1 `_cloud_receipt()` 写好了，`dispatch_verify()` 一次都没调过

`_cloud_receipt()` 早在 Issue #166 就落地了（读 Issue/PR 评论流判 `[接单]`），
注释写着"与 `_has_receipt()` 双轨互补"。可 **`dispatch_verify()` 里一次都没调用过它**：

```
云端真实场景：
  对端在 Issue 评论回 [接单]      → 平台可见 ✅
  本地 progress 表 accepted 事件  → 云端永远不会写 ❌
  dispatch_verify → _has_receipt() → False → 判「未回执」
  → 经理转小组长 → 上报"有活停在嘴上"
```

**对端明明接了单，判据说没接。** 双轨写了两条，一条从来没接上。

现在 `dispatch_verify(assignments, cloud=False)`：

| 返回值 | 含义 |
|--------|------|
| `receipt` | 本地 progress 事件 **或** 云端评论 `[接单]`，任一命中即真唤醒 |
| `receipt_source` | `local` / `cloud` / `local+cloud`，标明凭据来自哪一轨 |
| `cloud_degraded` | 评论流读不全/读取失败，**不静默判未回执** |

`cloud` **由调用方显式声明**，不做"有 issue 号就自动查"。这轮真踩到：

> `feature-verify/dispatch/真实唤醒校验闸门.sh` 拿 `issue_number: 109` 当夹具，
> 而 #109 的评论里恰好有真实 `[接单]`。自动查云一开，**夹具变成了活的**——
> "无回执任务"被外部真实数据判成已回执，三条断言全红。
> 假数据打真网络，测的就不再是代码，是别人仓库里恰好写了什么。

### 13.2 CI 抓到一个本地抓不到的：云轨被我多卡了一道 CLI

第一版给云轨加了 `_cnb_available()` 门槛。CI 直接红，而**本地全绿**：

```
本地   CLOUD True cloud True   ✓
云端   CLOUD False  False      ✗
```

差别只有一个：CI 镜像里**没装 `cnb` CLI**。可读回执走的是 `comment_stream` 的
HTTP + token，**跟 `cnb` CLI 一点关系都没有**：

```python
cloud = ... and _cnb_available() and ...   # ← 无关依赖，CI 下恒 False，云轨整条关闭
```

后果和 13.1 一模一样：明明该查云端 `[接单]`，却判「未回执」。
**我修了一个"用自己的假设作证"，顺手又写了一个"用自己的环境假设作证"。**

已去掉该门槛，可用性交给 `_cloud_receipt` 自己判（读不到进 `degraded`）。

### 13.3 顺手把仓库刷了 30 条垃圾单（自查）

`_run_role_engine()` 把需求文本/角色 prompt 当计划交给经理引擎，原先靠"探测不到 repo
就自动 dry_run"兜底。repo 探测一修，演练就变成了真派发：

```
跑一次全量测试 → 经理把「你是「架构·总师」…走「架构八步」：」当成一条任务，真建 Issue
→ #408–#437 共 30 条 CHORE:local-agent · role: 架构·总师 / task-xxx / "ok"
```

垃圾单标题就是证据：`as-a-i-want-so-that`（用户故事那行）、`given-when-then`（验收标准那行）
—— `parse_plan()` 把 prompt 每一行都切成了"任务"。

> **根因不是"忘了传参数"，是"用环境探测碰巧失败来代替显式声明"。**
> 这种正确最脆：不是被保证的，是被环境顺手施舍的，环境一变就翻。

五轮的 `live` 显式闸门（`live=True` / `CNB_MANAGER_LIVE=1`）正是这个方向的正解，两者一致。
30 条已全部留回指评论后关闭，不删除、不改标题。
