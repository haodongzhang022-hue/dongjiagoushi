# 通用派发能力（DispatchAbility · 全员能力）

> 本文描述**派发工作**这一高频复用模块能力的**全员化**设计：统一开发一次，
> 给每个 agent 对接上，让全员既会「派发」也会「接单」，从而构成真正可协作的体系。
>
> 对应 ISSUE #33 用户拍板：*派发工作这种能力是高频使用的复用的模块能力，应该统一
> 开发后，给每个 agent 都对接上，让他们都具备这个能力以及都具备这个能力的用法规则、
> 时机等，这样团队才是真正提高了能力上限，不然还是散兵，体系化后就是可协作的体系。*

---

## 一、为什么把派发能力全员化

在早期设计中，「派发工作」是**架构·经理的专属能力**（ManagerRole.dispatch()）。
但派发工作本质是**高频复用的模块能力**：

- 每个 agent 都可能**需要派发**——开发把子任务拆给其他人、测试把用例派给多节点、
  小组长把分支内容派给组员、总师把功能域拆给多个开发小组……
- 每个 agent 都可能**被派发**——收到接力卡后要能接单、开工、推进、交付。

若只有经理会派发，其他 agent 只能被动等活，团队就是**散兵**；
把派发能力**全员化**后，每个 agent 既是「派发方」又是「被派发方」，才是**可协作的体系**。

---

## 二、能力封装（DispatchAbility）

`local-agent/dispatch/ability.py` 提供通用能力类 `DispatchAbility`，
已默认挂载到所有角色基类 `BaseRole`，**任何角色实例都具备**：

### 作为派发方（L1→L4 四层深度闭环）

| 方法 | 层次 | 含义 |
|------|------|------|
| `dispatch(repo, assignments)` | L1→L4 | 四层分发一站式（声明→分发→触发→开工） |
| `dispatch_depth(...)` | 别名 | 同上 |
| `declare_assignments(...)` | L1 | 声明任务/角色 gid（登记在册） |
| `assign(...)` | L2 | 拆分任务 + 分配角色 + 投功能域池 + 创建独立 Issue |
| `trigger(...)` | L3 | 投递接力卡 `[触发:<角色>]`，等待 `[接单]` 回执 |
| `start(...)` | L4 | 确认接单后开工（in_progress + 留痕 + 执行 action） |

### 作为被派发方（接单闭环）

| 方法 | 含义 |
|------|------|
| `accept(task_key, agent_id, ...)` | 接单回执 `[接单]` → 标记 in_progress + 通知派发方 |
| `track_progress(task_key, agent_id, ...)` | 进度尺推进（写 goal_meters，供哨兵收敛判定） |
| `deliver(task_key, agent_id, output, ...)` | 向上交付（标记 done + 归档产物） |

### 能力声明

`capability()` 返回角色能力清单（含通用派发能力 + 使用规则），
供 AGENTS.md / 文档 / 各角色人设统一引用。

## 三、用法规则（谁都能用，但有边界）

派发能力全员化 ≠ 无序派发。**每个 agent 必须遵守以下规则**：

### ① 何时该派发（时机）

- **工作可拆为子任务、且有对应角色可承接** → 在自己的职责域内派发，不必等经理；
- **发现任务过大** → 一开始就拆分（`ops.split_task reason='initial'`）或申报加派；
- **面向同一问题需多角色协同** → 用 `peer` 同岗协作 / `pool` 功能域投池；
- **下游依赖已满足** → 立即派发（DAG 非直线，依赖满足即并行）。

### ② 何时该接单（时机）

- 收到带 `[触发:<角色全称>]` 的接力卡 → **必须回执 `[接单]` 确认接手**；
- 无回执不算 L3 完成；接单后进入 L4（开工 → 进度尺 → 交付）。

### ③ 不越权（边界）

- 派发须在**自己的职责域内**；
- **跨岗位派发**（如开发想派给测试/评审）须经**经理统一协调**，不越权直接指挥其他岗位；
- 收到派发却无法执行 → **显式上报**，不静默失败。

### ④ 防无效（留痕 + 哨兵）

- 同一任务二次触发仍同一 gid（稳定寻址不漂移）；
- 每次推进写 `goal_meters` 进度尺刻度（distance/delta）；
- 命中哨兵停滞/横跳/重复错误判定 → 按协议处置（打断/上报），不在同类失败上反复尝试。

### ⑤ 接单后必须继续工作（L4）

派发不是"分了就完事"——**要的是接单后真正继续工作的完整闭环**。
派发方须跟踪到 L4（接单回执 + 进度尺推进 + 交付），不以 L2/L3 为终点。

## 四、承载与兼容

- 承载引擎：`local-agent/dispatch_engine.py`（经理四层分发深度可执行引擎，L1→L4）；
- 能力封装：`local-agent/dispatch/ability.py`（`DispatchAbility` 通用能力类）；
- 全员挂载：`local-agent/roles/base.py`（`BaseRole.__init__` 默认挂载）；
- 经理复用：`local-agent/roles/manager.py` 通过 BaseRole 继承通用能力，保持对外 `dispatch()` 兼容。

> 向后兼容：既有 `dispatch_engine.dispatch(...)` 与 `ManagerRole.dispatch(...)` 接口不变，
> 新增的能力封装在其之上，不破坏已有调用。

---

## 五、验收口径

- ✅ 所有角色（BaseRole 子类）实例默认具备 `dispatch/accept/track_progress/deliver` 方法；
- ✅ 任意 agent 可在职责域内派发子任务并跟踪到 L4；
- ✅ 任意 agent 收到 `[触发]` 接力卡可回执 `[接单]` 并走完接单闭环；
- ✅ 经理作为分配调度核心统一协调跨岗位派发，能力与全员同源。
