# 分发递进深度模型（Dispatch Depth L1→L4）

> 本文件描述本仓库的分发机制从「声明」到「实际工作」的**四层递进深度模型**。
> 说明"声明/分发/触发/工作"这四个层次的差异与**我们真正要的层级（L4 工作）**，
> 以及每个层级需要的权限/触发/闭环条件。
>
> 对应 ISSUE #33 用户拍板：**只声明是最浅层的，要的是有递进关系、能触发接单、
> 接单后真正继续工作的完整分发闭环**。核心承载在 **架构·经理层**。

---

## 一、问题：分发"有"不等于"在工作"

分配下去之后，**不是有了负责的 agent 就行**，还得能触发后续的岗位激活、接单、开始工作。
仅声明/分配/触发都不够，**要的是他们接单后真的在继续工作**。

用户原话要义：

> "只声明是最浅层的，深一层是有分发了，再深是也触发他们接单了，再深是他们接单后工作。
> 不止有了负责的 agent，还有在继续工作的 agent 在工作。我们需要的就是最后的这个层次，
> 是有递进关系的。"

---

## 二、四层递进分发深度模型

| 层次 | 名称 | 含义 | 现状 | 是否达标 |
|------|------|------|------|----------|
| **L1** | **声明层** | 角色/任务被**定义声明**（settings.yml / team.yaml / issue 声明头存在） | ✅ 有 | 最浅，不够 |
| **L2** | **分发层** | 经理把工作**拆分成任务项**并**分配角色**（ops.enqueue_task / pool 投池 / gid 登记） | ✅ 有 | 只"分了"，没人做 |
| **L3** | **触发接单层** | 被分配角色被**触发激活**并**确认接单**（probe fire_signal / dispatcher router / 接力卡投递） | ⚠️ 部分有 | 有触发，缺接单确认闭环 |
| **L4** | **工作执行层** | 接单后**真正开始工作、持续产出、向上交付** | ⛔ 缺 | **我们要的层次** |

> **结论**：我们已有的机械能覆盖 L1~L3，但 **L4「接单后继续工作」** 是缺口——
> 有派发、有触发、缺「接单确认 → 开工 → 持续工作 → 交付」的完整执行闭环。

---

## 三、L4 工作执行层需要什么（闭环要素）

L4 不是"多一个开关"，而是把「接单 → 工作」的整条链路跑通。四个要素缺一不可：

### ① 接单确认（accept）

被派发的 agent 收到触发后，**必须回执确认接单**，才算完成 L3→L4 的跨越：
- 回执内容：`[接单] 任务 X 我接手了，目标 Y，计划 Z`
- 不确认 = 未真正接手；超时未接单 = 派发挂起，需经理介入重新派发或升级。

### ② 开工启动（start）

确认接单后，**有明确的工作环境与启动指令**：
- 有**可执行的工作载体**（repo 分支 / CI 任务 / 沙盒可运行脚本 / 对应的 issue）；
- 有**明确的第一动作**（先做 A 再 B，从哪开始）；
- 无载体、无启动指令 = 接了单也做不动（卡在"不知道从哪下手"）。

### ③ 持续工作（work & progress）

开始工作后**持续产出，且可被量化追踪**：
- 每次推进写入 `goal_meters` 进度尺刻度（`distance = goal_total - current`，`delta` 净进展）；
- 由 sentinel 判定是否停滞/横跳/重复错误，防无效努力；
- 由小组长监督本组进度尺收敛（group_oversight）。

### ④ 向上交付（deliver）

工作有阶段性成果时**按小组统一向上交付**：
- 产出发回 Issue/PR 评论留痕（可核验）；
- 经小组长汇总整合（team_lead_aggregate）；
- 看板自动可视化（DASHBOARD.md 自动刷新）。

---

## 四、权限与触发（让 L3→L4 真正能发生）

被派发的 agent 要有**可被召唤的权限**，才能触发接单、进而工作：

### 权限模型（@ 召唤格式）

| 触发方式 | 格式 | 说明 |
|----------|------|------|
| 云平台 @ | `@dongdongxiaozu/dongjiagoushi (架构·经理)` | 在仓库 Issue/PR 中 @ 对应角色全名，需**该角色有权限** |
| 平台兜底 | `@dongdongxiaozu/dongjiagoushi/CodeBuddy` | 官方 CodeBuddy 化身，可触发任意角色（需 `[触发:角色全名]` 接力卡标记） |
| 专用派活 agent | 一个**专门授权的派发/通知 agent** | 由它负责通知 + 派活 + 跑腿，拥有 @ 各角色的权限，其他人不越权 |

> **风险**：若只靠 @ 且 @ 的角色无权限，派发会静默失败。对策：**配一个专用派发 agent**
> （拥有 @ 各角色的权限），由它统一负责「派活通知 + 接单触发」，避免权限不足导致的派发断裂。

### 触发→接单→工作的完整链条

```
  L1 声明  ──▶  角色/任务被定义（settings.yml / team.yaml / issue）
  L2 分发  ──▶  经理拆分任务 + 分配角色 + 投功能域任务池（ops.enqueue_task）
  L3 触发  ──▶  派发 agent 触发目标角色（probe fire / dispatcher router / 接力卡投递）
  L4 工作  ──▶  [接单确认] → [开工启动] → [持续工作+进度尺] → [向上交付]
```

## 五、架构·经理层：分发职责的四层分工（本机制核心）

经理是分配调度核心。用户拍板要求**把本深度模型说明放入经理层**。经理分发时须**显式声明
本次分发所处的深度层级**，避免"以为分了就有人做"的误区：

### 经理输出契约补充（深度必填项）

每个被派发的任务项，经理**必须标注深度层级**：

| 深度层级 | 含义 | 经理动作 | 是否算完成 |
|----------|------|----------|------------|
| L1 声明 | 仅定义角色/任务 | 在 issue 声明头登记 | ❌ 未完成 |
| L2 分发 | 拆分+分配角色 | 拆任务、定负责人、投池（ops.enqueue_task） | ❌ 未完成 |
| L3 触发 | 触发接单 | 派发 agent 触发目标角色 + **等待接单回执** | ❌ 未完成（无回执不算） |
| **L4 工作** | 接单后持续工作 | **等待接单确认 → 开工 → 进度尺推进 → 交付** | ✅ **完成（最终目标）** |

**经理判定标准**：一个任务只到 L2（分了）不算完成；**必须到 L4**（有人接了单、在干活、
有进度尺推进、有交付）才算真派活成功。否则该任务是"名义派活"，须打回重派或升级。

### 经理协作纪律补充

- 经理分发任务时，**同时声明深度层级**（L1/L2/L3/L4），目标锁 L4；
- 经理对每个派发任务**跟踪到 L4**（有接单回执 + 有进度尺推进 + 有交付），
  不能以"我分了"为终点，要以"他做了"为终点；
- 无接单回执 / 无开工 / 无进度推进 = 派发断裂，经理须升级上报（哨兵 2 级 / 总师）。

## 八、真实唤醒校验闸门（Issue #100 · 防假装分配断链修复）

> 对应 ISSUE #100 用户痛点：秘书/经理/产品"列个表"调 `dispatch()` 就当完成，
> 实际没开 issue、没投递成功的交接卡、没唤醒 agent——却觉得自己算完成了。
> 根因：`dispatch()` 的 L3→L4 **自动无条件放行**，从不校验对端是否真实回执。

### 断链根因（定位到代码）

| 环节 | 断链表现 |
|------|---------|
| L3 触发 | `dispatch_trigger()` 只 `post_message` 往消息管线投一条 `[触发:角色]`，**不真实触达对端 agent** |
| L4 开工 | `dispatch_start()` **不等任何回执**，立即标 `working` 返回成功 |
| 无校验 | `dispatch()` summary 曾无条件报 `levels_reached=4`，`started_ok=N`，把"派发动作"当"派发结果" |
| 测试固化 | `test_dispatch_engine.sh` 曾断言"从未接单也 levels_reached=4"，把假装当验收标准 |

### 修复：真实唤醒校验闸门（已落地）

- **`_has_receipt(task_id, agent_id)`**：检测某任务对端 agent 是否真实回执 `[接单]`/`awake_ack`
  （progress 事件）。仅在消息管线投了 `[触发]` **不算唤醒**，必须对端回执才算真唤醒。
- **`dispatch_verify(assignments)`**：派发方/哨兵核验真实唤醒状态。返回
  `verified_all_awake` + `awaiting_receipt`（未回执任务明细）+ `awake_count` +
  `awaiting_receipt_count`。未回执即暴露，绝不静默放行。
- **`dispatch()` 语义修正**：L3 触发后校验——已回执的任务才放行 L4 开工；未回执的任务标
  `awaiting_receipt`（**不假装开工**），通过 `verification` / `awaiting_receipt` 显式暴露，
  summary 诚实统计 `started_ok` / `awake_count` / `awaiting_receipt_count`，**不再谎报 levels_reached=4**。
- **到达层级 max/min 两层（防混合场景歧义）**：混合场景（部分任务开工到 L4、部分未回执停在 L2）
  时单值 `levels_reached` 报 4 有歧义（会让调用方误以为全部到 L4）。summary 增加两层——
  `levels_reached_max`（任一任务最深到达层级）与 `levels_reached_min`（全部任务都已到达的
  保守层级）；`levels_reached` 保留为 min（向后兼容 · 不谎报）。
- **能力全员化**：`dispatch_verify` 已透传到 `DispatchAbility` + `BaseRole`，秘书/经理/产品/
  开发等任意角色都可调用，**不再"列个表就自认完成"**。

### 校验机制为什么必要

"列了清单 / 只投了接力卡 / 写了接力卡字段" 都不等于派发完成。真正完成 = 对端**真实回执
`[接单]` + 开工 + 进度尺推进 + 交付**。派发方必须用 `dispatch_verify` 核验，未回执任务
须重触发或升级（绝不静默放行），这才补上了"他们不检查后面交接卡和唤醒是否成功"的断链。

## 九、云端 ⇄ 本地 环境双轨语义边界（防机制互相覆盖）

> 对应 ISSUE #100 用户第二点担忧：本地 deepseek harness 与当前 CNB 云端 harness 机制不同，
> 若把本地版本同步/传输到云端，可能**用本地的"消息管线模拟唤醒"语义覆盖掉云端的"真实触发"语义**。

### 原则：云端与本地是**分环境双轨**，不是二选一互相覆盖

| 语义 | 云端（CNB harness） | 本地（deepseek harness） |
|------|--------------------|--------------------------|
| 真实唤醒 | **在 Issue/PR 发 `[触发:角色]` 接力卡**，由 CodeBuddy/NPC 语义触发对端真实执行 | 本地 `local-agent/` 消息管线 + 脚本触发 agent |
| 接力卡载体 | **CNB Issue 评论**（平台留痕、可核验回执） | `state/relay_card.json` / SQLite `messages` 表 |
| 回执 | 对端在 Issue **回复 `[接单]`**（平台可见） | `progress` 事件 `accepted`/`awake_ack` |
| 判定真唤醒 | 平台可见的 `[接单]` 回执 | `_has_receipt()` 查 progress 事件 |

**防覆盖纪律**：
- `local-agent/` 的 `post_message`（写 SQLite）在**云端语境下只是"模拟"接力卡载体**，
  不等于在 CNB 平台真实 `@` 出对端 agent；
- 云端真正"唤醒" = 在 CNB Issue/PR 落地 `[触发:角色]` 接力卡，由对端真实回执 `[接单]`；
- **同步代码/文档时不得用本地语义覆盖云端语义**——两套 harness 各自承载各自的环境；
- `dispatch_verify` 的 `_has_receipt()` 在校验"对端真实回执"这一判据上云端与本地对齐，
  云端以 Issue 平台的 `[接单]` 回执为准，本地以 progress 事件为准。
